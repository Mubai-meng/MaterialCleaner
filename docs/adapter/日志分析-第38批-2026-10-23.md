### 重要修正：`initialize()` 并没有卡 48 秒

第 36 批加 `initialize` 分步计时的动机是「33 秒内快照才可见、不知卡在哪」。本批日志的**表面现象**是主线程 `9439/9439` 从 07:23:42.120 到 07:24:30.771 零输出达 48.6 秒，很容易判成「主线程阻塞」。

但**这个结论是错的**，交叉验证推翻它：

- 07:23:47.332 MP 已经读到 `generation=3` 的 `configured_mount_points` 快照并推到 native。若 `initialize()` 真在 48 秒后才跑完 `publishAll()`，MP 在 07:23:47 不可能看到 gen=3。
- 07:23:48.940 health 已转 HEALTHY，要求 mp/fuse 层都拿到快照并同步。
- 主线程 07:24:30.771 的第一条是 `HookRecoveryCoordinator: performHooksReconnect`（由 07:24:29.751 的 `remove task` 击杀触发），**不是** `initialize` 的续行。

因此真实情况是：`initialize()` 在 07:23:43–47 之间就跑完了，`initialize done in ...` 那行连同各步耗时一起落进了被丢弃的 2947 行里。07:24:30.783 那份 gen=5 快照是击杀恢复路径重新发布的，不是首份。

**教训**：`initialize done in` 全通道 0 条 ≠ 没执行。这台机器开机 6 秒内必丢 2000–3000 行，任何「某行不在日志里」的判断都必须先用落盘产物（快照 generation、MP 侧 `loadConfiguredMountPoints`、health transition）反向验证时间点。这与第 37 批记下的纪律一致，本批再次踩到同一个坑。

## 四、唯一实质缺陷：`vfsNotMountedPids=3` 与 `bindMount result=true` 矛盾

### 现象

诊断包 `status/orchestrated_status.json`：

```
configuredPackages=7  mountedPackages=1
vfsObservedPids=115  vfsManagedPids=3  vfsUnmanagedPids=112
vfsMountedPids=0     vfsNotMountedPids=3
srStatus=com.quark.clouddrive:17878/10479/102;com.quark.clouddrive:18206/10479/102;com.quark.clouddrive:18209/10479/102
vfsCensusAt=1792711515701   (07:25:15.701)
```

三个 PID 的 flag 都是 `0x102` = `PID_FLAG_NOT_MOUNTED(1<<8)` | `PID_FLAG_STARTUP_AWARE(1<<1)`。

### 但挂载明确成功了

```
07:24:31.001 Mounter] bindMountLocked pkg=com.quark.clouddrive pid=17878 uid=10479 attempt=4 gen=5
07:24:31.016 Mounter] bindMount result=true pkg=com.quark.clouddrive pid=17878
             sources=[/storage/emulated/0/Download/Browser] targets=[/storage/emulated/0/Download/QuarkCloudDrive]
             nativeSource= nativeTarget= detail=success
```

18206 / 18209 同样 `result=true`（attempt=5 / 6）。三个进程在 07:24:31 之后持续存活（`Start proc ... for top-activity`，无重启记录），中间**没有任何 unmount 日志**，dmesg 里也没有与本项目相关的 mount/SELinux 拒绝（唯一相关 avc 是 `mmlistservice` 搜 `mediaprovid` 被拒，与挂载无关）。

### 判据在哪

`VfsLayerController.buildPidFlag()` 用 `PidMountClassifier.classify(targets.size, check_mounts(pid, targets))`：

- `targets.size == mountedIndices.size` → MOUNTED
- `mountedIndices.isEmpty()` → NOT_MOUNTED

而 `check_mounts`（`app/src/main/cpp/ProcInfo.cpp:128`）的做法是：读 `/proc/<pid>/mountinfo`，**找到第一个 target 行的位置**，再从该位置往后，逐行用 `IsTarget` 精确匹配 `targets[i]`。匹配不到就返回空数组 → 判 NOT_MOUNTED。

夸克的 source 是 `/storage/emulated/0/Download/Browser`、target 是 `/storage/emulated/0/Download/QuarkCloudDrive`。`Mount.cpp:815` 实际执行的是：

```cpp
mnt_source = (useSdcardFs ? "/mnt/runtime/write" : "/mnt/user/<user>") + source.substr("/storage".len)
mount(mnt_source.c_str(), target, nullptr, MS_BIND | MS_REC, nullptr);
```

即把 `/mnt/user/0/Download/Browser` bind 到 `/storage/emulated/0/Download/QuarkCloudDrive`。方向与规则语义一致（source 是用户写入路径，target 是进程可见路径）。

### 结论（2026-10-23 追补定论）：不是判据 bug，是**陈旧 pid 采样**

本节原先写的「普查口径缺陷 / 真缺陷」二分**已被实机证伪**，两个假设都不成立。

**证伪依据**：2026-10-23 10:20 用户在夸克应用详情页看到状态为**「已挂载」**，且全程没有「需要重新挂载」提示。而 UI 与普查走的是**同一个函数、同一个 flag**：

```kotlin
// StorageRedirectViewModel.kt:196   UI 详情页
CleanerClient.service?.getPackageStatus(packageName, PackageStatus.GET_FROM_ALL_PROCESS)
// VfsLayerController.kt:151         普查
enumerateSrProcesses(PackageStatus.GET_FROM_ALL_PROCESS)
```

两条路径最终都由 `buildPidFlag()` → `RuntimeFileUtils.check_mounts()` 判定。UI 现在判「已挂载」⇒ **`check_mounts` 判据本身正常**，`IsTarget` 精确匹配与 `splitLine.at(4)` 解析均无误。

**为什么 07:25:15 那一拍是 `NOT_MOUNTED`**：差别在**时刻**，不在判据。

- 三个 pid（17878 / 18206 / 18209）在 07:24:31 才启动（用户在 07:24:29.751 划掉任务后重开夸克），到 07:25:15 采样已过 44 秒；
- 2026-10-23 10:17 用户对同一批 pid 执行 `grep Download /proc/<pid>/mountinfo` 全部返回 **pid gone** ⇒ 进程早已不存在；
- `check_mounts` 对**已死 pid** 有两种结局：`/proc/<pid>/mountinfo` 打不开 ⇒ `nullptr` ⇒ `UNKNOWN(0x20)`；但 pid 若已被**复用**，文件的能打开、里面是别人的挂载 ⇒ 空数组 ⇒ `NOT_MOUNTED(0x100)`。

实测拿到的是 `NOT_MOUNTED` 而非 `UNKNOWN`，指向**第二种**。

**这就是普查侧的真实缺陷**：`buildPidFlag()` 直接拿 pid 读 mountinfo，**没有存活校验**；而同仓库的 `Mounter.bindMountLocked()` 早已为此加了防护：

```kotlin
// Mounter.kt:91-96 的注释原文
// ActivityManager 的进程列表可能包含刚被系统杀掉的陈旧记录（实测：网易云
// PID 25180 在 server 启动前 5 秒被 ColorOS o-stop(40) 杀掉，仍被 remountAll 选中）。
if (!ProcessIdentity.isAlive(pid)) { ... return false }
```

两处口径不一致：挂载侧会跳过死 pid，普查侧不会。修法是让普查侧对齐（见 §六 待办）。

> 注：pid 复用属于**推断**，不是直接实证（原始日志已被移走，无法回查）。但它能同时解释三件事：为何是 `NOT_MOUNTED` 而非 `UNKNOWN`、为何现在 UI 正常、为何只有普查这一拍异常。

### 为什么 `mountedPackages=1` 而 `vfsMountedPids=0`（并不矛盾）

`mountedPackages` 与「挂载成功」**无关**，之前理解为「已挂载包数」是错的。真源：

```kotlin
// Mounter.kt:702
fun getMountedPackages(): Set<String> = synchronized(lock) { mkdirRecords.keySet().toSet() }
```

`mkdirRecords` 只在 `auto_prepare_dirs()` **成功**时写入（`Mounter.kt:131-133`），语义是**「目标目录已就绪的包数」**。所以「`mountedPackages=1`（目录建好了）+ `vfsMountedPids=0`（普查这一拍没看到挂载）」完全自洽。

**命名有误导性**：`mountedPackages` 这个键名容易被读成「挂载成功的包」，实际是 mkdir 记录。这本身值得单独改名，但不影响行为，列入技术债。

### `nativeSource=` / `nativeTarget=` 为空是设计如此

不能拿它当「没挂上」的证据。native 成功路径刻意传 `nullptr`：

```cpp
// Mount.cpp 成功分支
write_mount_status(sock, make_mount_status(0, "success", 0, -1, nullptr, nullptr,
                                           MountPhase::COMPLETED));
```

只有失败时才回填这两个字段（给 `invalid_source` / `invalid_target` / `mount_rule` 定位用）。

## 六、本批不动代码（原始版本）＋追补订正

本批交付时未改动任何代码。**订正**：原文写的「`check_mounts` 的口径改变会影响 `mountForAllPackages` 的补挂载决策」是**错误归因**：

```kotlin
// VfsRuntimePolicy.kt:76
fun shouldMountForAllPackages(): Boolean =
    !isFuseBpfEnabled() && currentPolicy().behavior.recordExternalAppSpecificStorage
```

`mountForAllPackages()` 是**纯策略开关**，与 `check_mounts` 没有任何调用关系。`check_mounts` 的全部消费方只有两处：

| 消费方 | 作用 | 是否影响挂载行为 |
|---|---|---|
| `VfsLayerController.buildPidFlag()` | 喂 `getPackageStatus`（UI）与 `collectCensus`（诊断） | 否，注释明写「诊断投影，不驱动接管行为」 |
| `Mounter.checkAndRecordLocked()` | 决定是否重挂 | 是，但仅 `remountAllWithCheck()` 可达 |

而 `remountAllWithCheck()` 只在 `VfsLayerController.onStorageMounted()` 的**非主存储**分支触发（`isJustMounted && !isPrimary`）。本机不插 SD 卡 ⇒ 该路径永不进入。另外两个入口 `remountAll()`（`checkMountState=false`）与 `recordAll()`（`remount=false`，查完即弃）都不产生副作用。

**结论**：`check_mounts` 的返回值在本机只影响**显示与诊断**，改它没有挂载风险。
