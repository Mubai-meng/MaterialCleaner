### 重要修正：`initialize()` 并没有卡 48 秒

第 36 批加 `initialize` 分步计时的动机是「33 秒内快照才可见、不知卡在哪」。本批日志的**表面现象**是主线程 `9439/9439` 从 07:23:42.120 到 07:24:30.771 零输出达 48.6 秒，很容易判成「主线程阻塞」。

但**这个结论是错的**，交叉验证推翻它：

- 07:23:47.332 MP 已经读到 `generation=3` 的 `configured_mount_points` 快照并推到 native。若 `initialize()` 真在 48 秒后才跑完 `publishAll()`，MP 在 07:23:47 不可能看到 gen=3。
- 07:23:48.940 health 已转 HEALTHY，要求 mp/fuse 层都拿到快照并同步。
- 主线程 07:24:30.771 的第一条是 `HookRecoveryCoordinator: performHooksReconnect`（由 07:24:29.751 的 `remove task` 击杀触发），**不是** `initialize` 的续行。

因此真实情况是：`initialize()` 在 07:23:43–47 之间就跑完了，`initialize done in ...` 那行连同各步耗时一起落进了被丢弃的 2947 行里。07:24:30.783 那份 gen=5 快照是击杀恢复路径重新发布的，不是首份。

**教训**：`initialize done in` 全通道 0 条 ≠ 没执行。这台机器开机 6 秒内必丢 2000–3000 行，任何「某行不在日志里」的判断都必须先用落盘产物（快照 generation、MP 侧 `loadConfiguredMountPoints`、health transition）反向验证时间点。这与第 37 批记下的纪律一致，本批再次踩到同一个坑。

## 四、唯一实质缺陷：`vfsNotMountedPids=3` 与 `bindMount result=true` 矛盾

### 现象

诊断包 `status/orchestrated_status.json`：

```
configuredPackages=7  mountedPackages=1
vfsObservedPids=115  vfsManagedPids=3  vfsUnmanagedPids=112
vfsMountedPids=0     vfsNotMountedPids=3
srStatus=com.quark.clouddrive:17878/10479/102;com.quark.clouddrive:18206/10479/102;com.quark.clouddrive:18209/10479/102
vfsCensusAt=1792711515701   (07:25:15.701)
```

三个 PID 的 flag 都是 `0x102` = `PID_FLAG_NOT_MOUNTED(1<<8)` | `PID_FLAG_STARTUP_AWARE(1<<1)`。

### 但挂载明确成功了

```
07:24:31.001 Mounter] bindMountLocked pkg=com.quark.clouddrive pid=17878 uid=10479 attempt=4 gen=5
07:24:31.016 Mounter] bindMount result=true pkg=com.quark.clouddrive pid=17878
             sources=[/storage/emulated/0/Download/Browser] targets=[/storage/emulated/0/Download/QuarkCloudDrive]
             nativeSource= nativeTarget= detail=success
```

18206 / 18209 同样 `result=true`（attempt=5 / 6）。三个进程在 07:24:31 之后持续存活（`Start proc ... for top-activity`，无重启记录），中间**没有任何 unmount 日志**，dmesg 里也没有与本项目相关的 mount/SELinux 拒绝（唯一相关 avc 是 `mmlistservice` 搜 `mediaprovid` 被拒，与挂载无关）。

### 判据在哪

`VfsLayerController.buildPidFlag()` 用 `PidMountClassifier.classify(targets.size, check_mounts(pid, targets))`：

- `targets.size == mountedIndices.size` → MOUNTED
- `mountedIndices.isEmpty()` → NOT_MOUNTED

而 `check_mounts`（`app/src/main/cpp/ProcInfo.cpp:128`）的做法是：读 `/proc/<pid>/mountinfo`，**找到第一个 target 行的位置**，再从该位置往后，逐行用 `IsTarget` 精确匹配 `targets[i]`。匹配不到就返回空数组 → 判 NOT_MOUNTED。

夸克的 source 是 `/storage/emulated/0/Download/Browser`、target 是 `/storage/emulated/0/Download/QuarkCloudDrive`。`Mount.cpp:815` 实际执行的是：

```cpp
mnt_source = (useSdcardFs ? "/mnt/runtime/write" : "/mnt/user/<user>") + source.substr("/storage".len)
mount(mnt_source.c_str(), target, nullptr, MS_BIND | MS_REC, nullptr);
```

即把 `/mnt/user/0/Download/Browser` bind 到 `/storage/emulated/0/Download/QuarkCloudDrive`。方向与规则语义一致（source 是用户写入路径，target 是进程可见路径）。

### 待定：是普查口径问题还是真没挂上

两种可能，现有材料不足以二分：

1. **普查口径缺陷**：`check_mounts` 的成功判据要求 mountinfo 里存在 **target 路径**行。但 FUSE/ColorOS 17 下 bind mount 的可见性可能只体现在 `/mnt/user/0/...` 那一层，`/storage/emulated/0/Download/QuarkCloudDrive` 这一层在 mountinfo 里未必有独立行——若如此，所有重定向都会恒判 NOT_MOUNTED，属**观测缺陷**（能力本身正常，`mountedPackages=1` 又与之矛盾，需要先解释这个 1 从哪来）。
2. **真缺陷**：`bindMount result=true` 只代表 native `mount()` 调用返回 0（`Mount.cpp:851` 的 `ok == 0`），不保证目标进程命名空间里真的可见。若 goal 进程在 setns 之后又被 ColorOS 重置了命名空间，就会出现「报了成功但实际没挂上」。

**下一步取证**（不建议盲改）：
- 在 `bindMount result=true` 之后立即对同一个 pid 再调一次 `check_mounts`，把结果单独打一行。若立即复查也是空，说明是 native 侧真没挂上；若立即复查有值而 44 秒后没有，说明是后来被清掉（命名空间重置）。
- 同时 dump 该 pid 的 `/proc/<pid>/mountinfo` 里所有含 `Download` 的行，确认 bind 到底以什么路径出现（`/mnt/user/0/...` 还是 `/storage/emulated/0/...`）。

这两个探针都是只读、低频（每 pid 一次），可以安全加上。

### 为什么 `mountedPackages=1` 而 `vfsMountedPids=0`

`mountedPackages` 来自 `srStatus` 之外的另一条统计路径（包级 mount 记录），而 `vfsMountedPids` 来自普查的 PID 级 flag。两者口径不同、数据源不同，出现「包级 1 / PID 级 0」本身不必然是 bug，但结合上面 `0x102` 的值看，值得在本批一并查清。**本批不下结论、不改代码**。
