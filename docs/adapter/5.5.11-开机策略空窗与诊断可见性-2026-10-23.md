## 1. 开机策略空窗（真因与修复）

### 1.1 原判断是错的

第 43 批初版把空窗归因为「`HookPolicyRefreshScheduler` 的 `pollInterval=5000ms`，
首次失败后要等 5 秒才重试」。核对源码与日志后**不成立**：

| 事实 | 证据 |
|---|---|
| 调度器首轮**立即执行** | `HookPolicyRefreshScheduler.start()` → `scheduleNext(0L)` |
| 启动后 60 秒内是 **2 秒**间隔 | `HookRefreshIntervalPolicy.CONVERGE_INTERVAL_MS = 2_000L` |
| 5 秒只是 60 秒后的稳态值 | 日志 `pollInterval=5000ms` 打印的是常量，不是首轮延迟 |
| 那几轮其实**全是空转** | `initFromDataBus` 读不到快照时返回 `succeeded = true, changed = false` ⇒ `consumeAfterSignalCapture` 把水位推进；`DataBus.getSignalTimestamp` 不可读时返回 `0L` ⇒ `isStale()` 恒为 `0 > 0 = false` |
| 就算 `isStale()` 为真也没用 | 此刻 `HookDataBusBridge.callback` 仍是 null，`readSnapshot` 回落直读 `/data/local/tmp/cleaner`（uid=10326 无权）仍返回 null |

### 1.2 真因

```
17:03:35.853  server 9409  onStart: hooks binder not available yet, will retry
17:03:35.912  app    9031  BinderProvider.call: method=sendBinder      <- 只差 59 ms
      ...... 中间 10.16 秒，没有任何主动重试 ......
17:03:46.016  server 9409  [BinderSender] App process active, triggering server reconnection
17:03:46.018  server 9409  tryReconnect: connected
17:03:46.019  MP     9526  setCleanerServerBinder -> refreshFromDataBus -> gen 3/4 全部加载
```

`onStart` 失败一次后就放手，下一次尝试只能等 `whileAlive`（真正用到网关时）或
`BinderSender.onActive`（应用回到前台）。**开机时两者都不在窗口内发生。**

### 1.3 做法

新增 `HookBridgeStartupRetryPolicy`（纯策略，可 JVM 单测），`CleanerHooksClient.onStart`
失败后启动一条**有界短退避阶梯**：

| 尝试 | 1 | 2 | 3 | 4–8 |
|---|---|---|---|---|
| 延迟 | 200 ms | 500 ms | 1 s | 2 s |

总窗口 **11 700 ms**，成功即停。

- 执行线程：`HandlerThread("CleanerHooksStartupRetry")`，**只在阶梯真正启用时创建**
  （`establishConnection` 的 `ContentResolver.call` 可能拉起 app 进程，不能占主线程）；
- 取消：`startupRetryGeneration` 代次校验（`onStart` 成功 / `onDestroy` 时自增），
  已排队的任务见代次不符立即返回；
- 不经过 `tryReconnect` 的节流，也不污染 `lastBridgeAttemptUptimeMs`；
- **稳态零开销**：阶梯只在 `onStart` 失败后跑有限次，跑完就退出。

### 1.4 预期

本次样本 `onStart` 只差 59 ms 就拿到 binder ⇒ **第 2 次尝试（+200 ms）即连上**，
空窗从 7.55 s 压到 **0.2 s 量级**。

## 2. `HookBridgeRegistrar` 的「Provider 未就绪」降 W

### 现象

一次开机窗口内 `HookBridgeRegistrar` 产出 **17 行 E**，其中 12 行是堆栈：

```
17:02:44.441 W HookBridgeRegistrar: Registry binder died, requesting re-register
17:02:44.569 W HookBridgeRegistrar: Failed to fetch registry binder
17:02:44.569 W ... (12 行堆栈)
17:02:44.574 E HookBridgeRegistrar: Failed to register hooks callback
17:02:44.574 E ... (12 行堆栈)
17:02:44.574 E java.lang.IllegalArgumentException: Unknown authority me.gm.cleaner.hooks_bridge
```

同窗口真实故障数为 **0**。与 5.5.9 处理的 `HOOK.JAVA.BINDER.DEAD` 完全同型。

### 做法

新增 `BridgeRetryableFailurePolicy`（纯策略）：只认
`java.lang.IllegalArgumentException` + 「查不到 Provider」话术
（`Unknown authority` / `Failed to find provider` / `Unable to find provider` /
`Could not find provider` / `Failed to find provider info`，大小写不敏感）。

| 分支 | 级别 | 堆栈 |
|---|---|---|
| `retryable=true`（Provider 还没注册） | **W** | 不打（话术恒定，无新信息） |
| `retryable=false`（认不出的异常） | E | 打 |
| `provider_acknowledged_false`（ack 明确 false） | E | 打 |
| `HOOK.JAVA.REG.EXHAUSTED`（突发预算耗尽） | **E（本次由 W 升上来）** | — |

### 为什么把「预算耗尽」升 E

per-attempt 降 W 之后，若 Provider **永远**不出现（app 被卸载 / 组件被禁用），
不再有任何 E 会亮。`BridgeRegistrationRetryPolicy.MAX_BURST_ATTEMPTS = 6` 次全失败
才是判定「这不是窗口，是真故障」的唯一客观依据，因此把它的 severity 从 W 提到 E。
**降级与升级是成对的**，单做任何一半都会让某类问题静音。

### 反向保护

`BinderDeadSeverityContractTest` 的判据从「WARN 只要出现就赢」改为「最近的
severity 字面量胜出」（两条相邻分支必须各归各位），并新增 3 条正向 + 1 条反向断言，
其中 `retryable=false 仍是 E` 与 `重试预算耗尽升级为 E` 是防「后人手滑把真故障一起降级」
的守卫。

## 3. 实时值加 `recordedPidsAt`

### 现象

`recordedPids=0` 与 `vfsMountedPids=4` 并列，第 42、43 批**连续两次**被读成
「模块自相矛盾」。两次的真实成因都是采样时点不同：

| 指标 | 来源 | 时点 |
|---|---|---|
| `recordedPids` / `preparedPackages` / `mountTotalAttempts` | `collectReport` 当场读 `Mounter` | **实时** |
| `vfsObservedPids` / `vfsMountedPids` / `srStatus` | `collectCensus`，`CENSUS_THROTTLE_MS = 30_000L` 内复用 | **30 秒节流缓存** |

### 做法

- `orchestrated_status.json` 的 `vfs` 段新增 `recordedPidsAt`（epoch ms，与
  `vfsCensusAt` 同一时钟域，取 `collectReport` 的 `now`）；
- `VfsReportKeys` 新增 `RECORDED_PIDS` / `RECORDED_PIDS_AT` 常量（键契约单一真源）；
- `VfsProcessCensus` 的 `vfsMountedPids` / `vfsCensusAt` 改为常量引用，不再散落字面量；
- 概览（`summary.txt` / `summary_zh-CN.txt`）新增一行，**并列两个时点与相差毫秒**，
  数值不同且 skew ≥ 0 时直接标注 `different instants — NOT a contradiction`：

```
- VFS sampling: realtime recordedPids=0 @1792746414662 vs census vfsMountedPids=4 @1792746385973, skew=28689ms (different instants — NOT a contradiction)
```

- 缺任一时点就**不打印**（宁可不输出，也不给出可能错的差值）。

## 4. boot log 裁剪加 `### REPLAY` 段

### 现象

`-b crash` 会让 logd 把 ramoops 里**几周前**的崩溃行重放进当前缓冲区
（第 42 批与第 43 批都抓到 `11-10 12:57:13 pid 1220 (init)` 冒出到 10-23 的会话里）。
这类行大多也是 `E`/`F`，混在 CRITICAL 段里造成两个后果：

1. **首末时间戳算出负跨度** —— 段首是本次会话、段尾却是三周前，「覆盖了多久」直接算错；
2. 抢占 CRITICAL 预算，稀释本次会话真正的错误证据。

### 做法

- 会话日期 = 文件里出现次数最多的 `MM-DD`（`dominantDate`，重放行必然只占极少数；
  同票取较晚那天）；
- 时间戳日期 ≠ 会话日期的行归 `LineClass.REPLAY`，**优先于** E/F 判定；
- REPLAY 单列到末尾 `### REPLAY (other dates, NOT this session — excluded from the timeline above)`，
  吃「剩余预算」里的 5%（`REPLAY_PERCENT = 5`，按需收敛，不挤压前三段比例）；
- 无重放行时**不输出**空段（多数文件没有，空标题只是噪声）；
- 头部 `lines=` 追加 `replay=`，`step=` 追加 `replay=`，保持「丢了什么」可自证；
- `classify(line, tagSet)` 旧重载保留（`sessionDate = null` ⇒ 不识别 REPLAY），
  行为与 5.5.10 逐字一致。

## 5. 明确不改（附理由）

| 候选 | 不改的理由 |
|---|---|
| `HookPolicyRefreshScheduler` 首轮间隔 | 那几轮本身空转（§1.1），改快只是往空转循环里加约 40 次无结果的 Binder/文件读 |
| `isStale()` 把「快照缺失」当未消费 | 会让「确实没有该类快照」的场景每轮重试一次文件读，把单点问题扩散到稳态路径 |
| 让 MediaProvider 直读 `/data/local/tmp/cleaner` | 要改 DataBus 目录权限模型，动到沙箱/权限假设 |
| REPLAY 段按 tag 白名单分流 | 日期是唯一客观判据；tag 无法区分「旧日期的本项目行」 |

### 本轮踩到的两个编译坑（已固化进注释）

1. **`cleaner-server` 的 `android.os.Handler` 被 `hidden-api-stub` 的最小桩遮蔽**：
   该桩只有 `Handler()` / `Handler(Looper)` / `post` / `postDelayed` / `getLooper` 五个方法。
   `removeCallbacksAndMessages` 写了就是 `Unresolved reference`。取消改用
   「代次校验 + `quitSafely()`」。
2. **属性与同名函数不能并存使用**：`private var startupRetryHandler` 与
   `private fun startupRetryHandler()` 同名时，方法体里靠后的属性访问会解析歧义。
   函数改名 `ensureStartupRetryHandler()`。
