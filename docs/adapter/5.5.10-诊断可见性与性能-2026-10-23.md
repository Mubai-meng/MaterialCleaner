## 1. 修复一：`initialize` 分段耗时双写

### 1.1 缺陷事实

`LayerOrchestrator.initialize()` 结尾那行

```
initialize done in 4951ms (gateway=…, observers=…, pkgReceiver=…, autoLogging=…,
publishAll=…, remount=…, hookRefresh=…, binder=…, scheduler=…)
```

是「启动花了多久、卡在哪一步」的**唯一**答案来源。但 ColorOS 17 的 `LOG_FLOWCTRL`
按进程限额丢日志：

- 第 41、42 两批**全包检索命中 0 次**（`cleaner.log` + 两份 boot log +
  `logcat_threadtime_recent.txt` 均无）；
- 而函数**确实已跑完** —— `started=5/5`、`auto logging started`、
  `DataBus initialized at`、事件游标推进到 `…7253` 全都有独立证据。

⇒ 结论：**「没有这行」不等于「没执行」，而是这个问题在实机上永远无法回答。**
它直接决定兼容层多久从 `RECOVERING` 转 `HEALTHY`（第 41 批实测 initialize start →
首份 `redirect_policy` 快照相隔 33 秒，同期丢 2700+ 行，完全无法定位）。

### 1.2 实现

新增 `orchestrator/StartupTiming.kt`（object，纯内存事实）：

```kotlin
object StartupTiming {
    val SEGMENT_ORDER: List<String>   // 九段固定顺序
    data class Snapshot(attempt, startedAtWallMillis, completedAtWallMillis,
                        elapsedMs, segmentsMs)
    fun record(startedAtWallMillis, elapsedMs, segmentsMs)
    fun toJsonOrNull(): JSONObject?   // 未记录返回 null，不写空对象
}
```

接入点：

| 位置 | 改动 |
|---|---|
| `LayerOrchestrator.initialize()` | 九段耗时先装进 `linkedMapOf` → `StartupTiming.record(...)` → **再**打日志（日志行格式与历史逐字一致，改由同一批键生成） |
| `RuntimeStatusAggregator.renderStatusJson()` | 追加 `"startupTiming"` 段；未完成时**不写该键** |
| `DiagnosticSummary.appendStartupTiming()` | 摘要里一行 `- Startup: elapsed=…ms (gateway=…, …)` / 中文版同 |
| `DiagnosticSummary.appendKeySignals{,ZhCn}()` | 在「三层缺任一层就 return」**之前**调用（启动耗时与层状态无关） |

设计取舍三条：

1. **为什么写内存不写盘**：写盘会再次依赖 DataBus 的原子写 + fsync 路径，且在
   `publishAll` *之前*执行会引入顺序依赖。诊断包读的是 `collectStatusJson()` 的
   **实时内存值**，不受日志是否被丢弃影响。
2. **缺段写 `-1` 而不是省键**：省键会被读成「该段不存在」，`-1` 明确表示「未采集」。
3. **多次 `initialize` 只留最后一次**，`attempt` 计数保留「这是第几次」；
   `record` 拷贝入参 Map，调用方后续改动不会渗入快照（有单测）。

快照形态：

```json
"startupTiming": {
  "attempt": 1,
  "startedAtWallMillis": 1792737288765,
  "completedAtWallMillis": 1792737293716,
  "elapsedMs": 4951,
  "segmentsMs": { "gateway": 120, "observers": 800, "pkgReceiver": 3,
                  "autoLogging": 45, "publishAll": 210, "remount": 1500,
                  "hookRefresh": 60, "binder": 12, "scheduler": 5 }
}
```

## 2. 修复二：boot log 分级裁剪

### 2.1 缺陷事实（第 42 批实测）

`cleaner-boot-*` 是 `-b main,system,crash` **无 tag 过滤**的全系统日志：

| 事实 | 数值 |
|---|---|
| 60 秒产出 | **7,249,920 B = 118 KB/s** |
| 归档预算 | `MAX_TEXT_FILE_BYTES` = 512 KiB |
| 实际覆盖窗 | 512 KiB ÷ 118 KB/s ≈ **4.3 秒** |
| 实测 `.log` | 14:35:14.233 – 14:35:15.203 = **0.97 s** |
| 实测 `.log.1` | 14:35:00.539 – 14:35:03.432 = **2.89 s** |

⇒ 起机关键窗口（init/zygote/framework 启动、首轮挂载、策略首次可见）**结构性不可见**。

**为什么不能简单改成「头尾各半」**：那只是把 4.3 秒变成「前 2.2 + 后 2.2」，
中间 55 秒照样消失，而挂载失败、Hook 未加载恰好落在中段。**必须保留时间轴。**

### 2.2 算法

新增 `DiagnosticBootLogTrimmer.kt`，按行三级分类：

| 级别 | 判定 | 处置 |
|---|---|---|
| CRITICAL | level ∈ {`E`,`F`} | 优先保留，占可用预算 65% |
| FOCUSED | tag ∈ `LogTagFilter.tagSet` | 次优先，占 25% |
| NOISE | 其余 `V/D/I/W` | 吃剩余预算，**均匀采样**只保留时间轴骨架 |

每类按 `ceil(该类总字节 ÷ 该类预算)` 算步长，**从该类第一行起等间隔抽样** ⇒
输出时间轴覆盖完整窗口，密度下降但「哪一秒开始不对劲」始终可答。

解析兼容三种 logcat 格式（`threadtime` 是 `-f` 的实测默认；另两种是为将来改
`-v` 兜底）；续行（不以时间戳开头）**跟随其头行同命运**，避免孤儿堆栈行。

### 2.3 预算与输出契约

`MAX_BOOT_LOG_BYTES = 1536 KiB`（新增，替换 boot 段沿用的 512 KiB）：

- 依据：实测 `E/F` 约占 12% 字节 ≈ 860 KB（7.2 MB × 12%）；
  1536 × 65% ≈ **995 KB > 860 KB** ⇒ **E/F 能全留（step=1）**；
- 降到 512 KiB 会让 E/F 自己就被采样，等于回到「证据随机丢弃」；
- 最多 2 个 boot 分片 × 1536 KiB ≈ 3 MB，包体增量可接受。

输出结构（logcat 原行**逐字保留**，可直接 `grep`）：

```
path=… size=… modified=…
retention=critical(E/F)+focused(project tags)+noise(uniformly sampled)
lines=total=55123 critical=5400 focused=812 noise=48911 continuation=23
budget=maxBytes=1572864 criticalBytes=864312 continuationBytes=9120 …
step=critical=1 focused=1 noise=12 (0 = dropped for lack of budget)
### CRITICAL (level E/F, verbatim)
…
### FOCUSED (project tags, verbatim)
…
### NOISE (time axis only) sampled 1/12
…
```

`manifest.txt` 的 `truncation=` 同步改为 `keptTiered=…B overBudget=…B`
（不再用 `keptFirst`——boot 段不是砍头），`auto_logging_manifest.txt` 增加
`budget=bootTiered(…)B+ringHeadTail(…)B`。

### 2.4 单测抓到的真缺陷（本轮）

第一版把「续行字节」漏在 `Scan` 之外，而硬上限是 `预算 × 1.5` ⇒ **崩溃堆栈被截断**：
3 行堆栈只保留了第 1 行（`continuation lines follow their header line` 失败）。
修法：

- `Scan` 增加 `continuationBytes`，`planBudget` 用 `criticalBytes + continuationBytes`
  作为 CRITICAL 需求（续行几乎全部跟随 `E/F` 头行）；
- 硬上限从 `×1.5` 放宽到 `×2` —— 它只是「估算失真的兜底」，精确控制交给 step。

> 这就是「纯函数一律补单测」的价值：堆栈截断在实机上会被读成「崩溃信息不全」，
> 而不会指向裁剪算法。

## 4. 性能梳理：全项目走一遍，落地 2 项、明确不改 8 项

### 4.1 落地

#### P-A：`ActivityManagerLogsObserver` 每行解码（server 进程，实测 700–1500 行/s）

```java
// 旧：每行都执行
final var parsedStart = parseStartProcLine(line, new String(amStartProc));
…                       parseKillingLine(line, new String(amKilling), new String(phantomProcessRecord));
```

三个常量是混淆后的 `char[]`，**旧实现在每行解析时现场 `new String(char[])`**。
本通道实测 700–1500 行/s ⇒ 每秒上千次解码 + 等量短命 `String`，纯属给 server
进程抬 GC 压力。改为在 `mExecutor.execute(...)` **之前**解一次，三个变量此后只读。

> 语义零变化（同一份字符内容），只是把分配从「每行」降到「每次 attach」。

#### P-B：`FuseRedirectStats.prefixOf` 每命中都造垃圾（MediaProvider 热路径）

旧实现：

```kotlin
path.split('/').filter { it.isNotEmpty() }            // 6 段 String + List
    .let { if (it.size <= max) it else it.take(max) } // 又一个 List
    .joinToString("/")                                // 结果串
+ 上层 1–2 次 substring(trimmed / dir)
```

对 `/storage/emulated/0/Download/a.apk` **单次十余个短命对象**。调用方
`FuseRedirectCounters.record` 跑在 FUSE 热路径（每个未命中路径一次），相册/媒体
扫描时可达上千次/秒。

两项改动：

1. `capSegments` 重写为**零中间分配扫描**（只留 1 个结果 String + 1 个缓冲），
   `prefixOf` 不再切 `substring`，直接把「有效区间终点」传下去；
2. `record` 增加**同 path 短路**（`@Volatile lastMissPath`）：同一路径反复访问是
   MediaProvider 常态（一次查询链会问很多次），内容比较（零分配）远比重算前缀便宜。

等价性由 `FuseRedirectStatsTest` 原有 8 组用例（空串 / 纯斜杠 / 连续斜杠 / 段数上限 /
相对路径 / 目录尾斜杠）+ 新增边界用例守住；`FuseRedirectCountersTest` 钉住
「短路不改变 `lastMissPrefix` / 计数」。

### 4.2 已评估、明确不改（收益低于风险或语义代价）

| # | 候选 | 为何不改 |
|---|---|---|
| 1 | `VfsProcessCensus.toMetrics()` 每 2s 重建 15 项 map | 微秒级；加 `lazy` 缓存等于为一个不可测量的量引入状态 |
| 2 | `collectStatus()` 每 2s 五层采集 + 2 次 Binder ping | 量级约 0.0025% CPU；`publishStatusSnapshot` 已有语义脏检查，采样本身必须实时 |
| 3 | `captureInstanceSnapshot` 30s 扫 119 个 `/proc/<pid>/stat` | 改为「先归属过滤再采快照」会动挂载判定的执行顺序（第 38 批教训），收益仅 ~4 syscall/s |
| 4 | `pruneLocked` 只在采集启动时跑 | 会话内磁盘上限由 `logcat -r/-n` 硬保证（32 MB + 4 MB + 16 MB），再加定时器是重复保险 |
| 5 | boot 段 60s 无 tag 过滤（7.2 MB/次启动） | 它是「白名单漏登记某 tag」的唯一兜底现场；加过滤等于把兜底关掉。改为在**归档侧**分级裁剪（§2） |
| 6 | `HookPolicyRefreshScheduler` 5s 轮询 | 已由 `HookRefreshIntervalPolicy` 做收敛 2s / 稳态 5s 分级，且首轮立即执行；稳态 stat 4 个 signal 文件 ≈ µs |
| 7 | `EventSignalCoalescer` 250ms 限流 | 已把单窗口 50 条 signal 压到 ≤4/s，且尾沿必达 |
| 8 | `DataBus.writeSnapshot` 每轮 fsync | 已有语义脏检查（`semanticKey`），实测把 105 次重复写降到「语义变化才落盘」 |

### 4.3 结论

性能热点在**第 27–33、38–40 批**已集中优化过一轮（ThreadLocal 串数据、图标缓存、
`policyRuleCountIndex`、census 30s 节流、signal 合并、快照脏检查、白名单压缩两个数量级）。
本轮新增的两项都在**每行/每次调用**级别，属于「单位成本 × 极高频率」那一类，
也正好是此前审计没覆盖到的两处。

## 5. 未闭环

1. **5.5.10 两项修复都需要下一次覆盖安装才能验证** —— 覆盖安装后到重启的窗口跑的是
   旧字节码（LSPosed 在 zygote 期读成 `InMemoryDexFile`），这是本项目已实证六次的规律。
   判据：
   - `orchestrated_status.json` 出现 `startupTiming` 段（且 `attempt` 与启动次数一致）；
   - `logs/auto/cleaner-boot-*.log` 首部出现 `retention=critical(E/F)…` 与
     `step=critical=1`，且时间跨度接近 60 秒（而非 4 秒）。
2. **boot 段分级裁剪的实际压缩比**待实测：预期 7.2 MB → ≤1.5 MB，`E/F` 全留。
   若 `E/F` 实际占比高于 12%，`criticalStep` 会 >1（会在 `step=` 行显式可见）。
3. `addFileHead` 现无调用点（boot 段已改分级裁剪），保留并注明「不要用于启动段」。
   若将来确认无其它用途，可一并删除以减少审计歧义。
