### 3.2 因果链（三步，缺一不可）

```
① 5.5.12 给 HooksBridgeProvider 加 android:directBootAware="true"
   ⇒ 用户解锁之前 AMS 就安装该 provider ⇒ 触发创建 me.gm.cleaner 进程
     （这是 5.5.12 修开机握手的正确做法，本身没问题）
                ↓
② 5.5.13 在 App.onCreate 加了 SelfHidingPreferences.reconcileOnStartup(this)
   而 SelfHidingPreferences.prefs() 用的是 **裸 this**（CE 存储）
   ⇒ Direct Boot 窗口内 getSharedPreferences 抛 IllegalStateException
                ↓
③ Instrumentation.callApplicationOnCreate 抛 ⇒ Application 创建失败
   ⇒ 整个进程被判定为启动失败 ⇒ 后续所有 provider/activity 全部不可用
   ⇒ App 永远拿不到 server binder ⇒ UI 显示「存储重定向未运行」
```

### 3.3 铁证：5.5.12 的 `App.onCreate` 全部用 DE context，只有我加的那行用裸 `this`

```kotlin
// 5.5.12 (e2188b7) —— 全部走 dpsContext，解锁前后都安全
override fun onCreate() {
    super.onCreate()
    AppLabelCache.init(this)
    val dpsContext = createDeviceProtectedStorageContext()   // ← 关键
    RootPreferences.init(dpsContext)
    ServicePreferences.init(dpsContext)
    ServiceMoreOptionsPreferences.init(dpsContext)
    ServiceBootStateStore.init(dpsContext)
    ClientErrorJournal.init(dpsContext)
    ServerStateMachine.init(this)
    ...
}
```

5.5.13 的 diff 只加了三行，**且是唯一一处传裸 `this` 的**：

```diff
         ServerStateMachine.init(this)
+        // 覆盖安装后 alias 的 enabled 状态可能被重置回 manifest 默认值 ⇒
+        // 用户勾了「隐藏桌面图标」却在升级后又看到图标。这里按偏好重放一次，幂等。
+        SelfHidingPreferences.reconcileOnStartup(this)     // ← this = CE context
```

### 3.4 为什么第 45 批（5.5.12）没崩

因为 5.5.12 的 `App.onCreate` 里没有任何 CE 读写。**这个崩溃是 5.5.13 独有的**，
与第 45 批已修的「回调未注入」是**两个独立缺陷**，只是表现相似（都显示降级/未运行）。

### 4.2 UI 为什么显示「未运行」

`ServiceStatusFormatter.fallbackTitleRes()` 在 `orchestrated == null` 时按 `serverState`
落 `service_status_not_running_title`。而 `orchestrated` 的取值是：

```kotlin
val orchestrated = orchestratedStatus.takeIf { serverState == ServerState.RUNNING }
```

**App 进程刚创建就崩了 ⇒ `ServerStateMachine` 从未进入 RUNNING ⇒ 走 fallback ⇒ 显示「未运行」。**
这与 server 的真实状态无关 —— 是 App 侧「看不见」而非 server「不在」。

### 4.3 诊断包为什么是 fallback

`summary_zh-CN.txt` 首行即 `Material Cleaner 诊断包概览（App fallback）`，
`serverConnected=false`、`serverVersion=-1`、`orchestratedStatus=unavailable`。
**但 `databus/` 目录下的六份快照全部读到且 `validJson=true`** —— 这恰好反证
server 在写、文件系统通、只有 Binder 断了。app UID 10354 能读 `/data/local/tmp/cleaner`
（`health.json` 的 15 条 `permissionIssues` 全是 `:write`，app 本来就不该写）。

## 5. 版本对账：`STALE_SERVER: app=563 server=561 hook=561 installed=563`

```
10-24 11:04:24.835  5324  5417 W MC/StateMachine: stale version detected (STALE_SERVER):
    app=563 server=561 hook=561 installed=563
```

以及 `native_hook_status.json` 的 `"hookVersionCode": 561`。

### 5.1 这是完全的预期行为，不是缺陷

- 用户装的是 **5.5.13（563）**；
- server 进程从 `09:02:45` 就在跑，跑的是 **5.5.11（561）** 的旧字节码；
- Hook 住在 MediaProvider（zygote 派生），同理是 561。

这**完全符合**既定认知：「覆盖安装后到重启的窗口跑的是旧字节码」。
5.5.11 的 server 与 5.5.13 的 app 互通时，`serverVersion != installed` ⇒ 落 STALE_SERVER，
UI 应提示「请重启手机」。本次没有显示该提示，因为 App 进程崩了、走不到这段逻辑。

### 5.2 为什么本批能看到 5.5.13 的修复生效

`11:04:19.899` 有一条**极其关键**的日志：

## 7. 「找不到开关」的正解

### 7.1 设置页没有被隐藏

截图显示顶部三个 Tab 齐全：`存储重定向` / `文件系统记录` / `更多选项`。
用户当前停留在**第一个 Tab**，而两个开关在**第三个 Tab 的最底部**。

### 7.2 开关确实已在 APK 里

`service_more_options_preferences.xml` 末尾（`about` 之后）已加：

```xml
<PreferenceCategory android:title="@string/self_hiding_header">
    <SwitchPreferenceCompat android:key="@string/hide_desktop_icon_key" ... />
    <SwitchPreferenceCompat android:key="@string/hide_recents_key" ... />
</PreferenceCategory>
```

且 `MoreOptionsFragment.bindSelfHidingPreferences()` 有 `findPreference<...>() ?: return` 的
**静默失败**分支 —— 如果 `key` 解析不到会整段跳过、不报错。这是设计缺陷（见 §8 待办）。

### 7.3 用户为什么会以为「被隐藏」

因为 App 进程反复崩溃重启，用户点到「更多选项」时内容可能还没加载完，
加上开关在最底部需要滚动，就误判为「页面被隐藏」。
**根因还是 §3 的崩溃**。

### 守卫测试的 4 条

1. `SelfHidingPreferences 的偏好必须建在设备加密保护存储上`
2. `SelfHidingPreferences 读写偏好都不得向外抛异常`
3. `App onCreate 里不允许出现裸的 CE 偏好读取`
4. `HooksBridgeProvider 仍是 directBootAware`（**反向守卫**：防止有人为了绕开本崩溃而撤掉
   `directBootAware`，那会退回第 44 批「解锁前 provider 不在 AMS 里」⇒ 开机握手 3.76 s 全失败）

第 1 条做过**反向验证**：临时把 `prefs()` 退回 CE 存储 ⇒ `AssertionError` 如期出现；恢复后全绿。
