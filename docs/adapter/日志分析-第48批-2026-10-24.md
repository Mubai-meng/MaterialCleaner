## 4. 新发现问题

### 4.1 【确凿缺陷】`cleaner-crash.log` 全程 0 字节，尽管 crash buffer 有内容

**证据链（三重独立）**：

1. **手机文件系统**（`commands/auto_logs_tree.txt`）：
```
-rw------- 1 root root 0 2026-10-24 14:07 cleaner-crash.log
```
mtime 停在 **14:07**（= 第 47 批那次会话），本批两轮启动（20:03:11 / 20:03:56）**都没更新它**。

2. **归档内**（`logs/auto/cleaner-crash.log`，83 B）：
```
path=/data/local/tmp/cleaner_logs/cleaner-crash.log
size=0
modified=1792822034378        ← = 14:07:14.378
```
83 B 全部是 `addFileHeadAndTail` 的元数据头（`DiagnosticFileSection.kt:224-232`），正文为空。

3. **crash buffer 确实有内容**（`logs/logcat_crash_recent.txt`，独立执行 `logcat -d -b crash -t 2000`）：
```
11-11 18:26:03.731 F libc: Fatal signal 6 (SIGABRT) ... pid 1196 (init)
10-24 20:03:52.583 F libc: Fatal signal 6 (SIGABRT) ... pid 8254 (init)    ← 本批！在 crash 通道启动前
10-24 20:06:25.176 F libc: FORTIFY: pthread_mutex_lock called on a destroyed mutex (0x7784fbf390)   ← 本批！在 crash 通道启动后
```

**`20:06:25.176` 这条是关键**：它在 crash 通道启动（20:03:56.665）**之后** 2.5 分钟才产生，crash 通道若正常工作就**应该**写进 `cleaner-crash.log`。但它没有。

**命令本身是对的**（源码核对）：
```java
// AutoLogging.java:487-497
static String[] buildCrashLogcatCommand(final String logPath) {
    return concat(new String[]{"/system/bin/logcat", "-f", path,
                    "-r", "2048", "-n", "2"},   // 2 × 2 MB 旋转
            LogTagFilter.crashChannelArgs());   // → arrayOf("-b", "crash")   【LogTagFilter.kt:107】
}
```
无 tag 过滤、`-b crash` 明确 —— 与 `logcat_crash_recent.txt` 用的 `-b crash` 一致，后者读得出、前者写不进。

**同时刻的对照实验**：boot 通道用 `-b main,system,crash`，**成功**写到了 crash 段内容：
```
cleaner-boot-1792843436665.log.1:1:  --------- beginning of crash
cleaner-boot-1792843436665.log.1:2:  11-11 18:26:03.731 F libc: Fatal signal 6 ...
cleaner-boot-1792843436665.log.1:4818: 10-24 20:03:52.583 F libc: Fatal signal 6 ...
```
⇒ 不是 SELinux 拒、不是文件权限、不是 logd 不可读。

**唯一仍未排除的嫌疑**：`logcat -b crash -f <file>` 的写入时机。`logcat -f` 默认按块缓冲，`-b crash` 这个 buffer 在**没有新崩溃时几乎不产生输出流**，logcat 可能一直不 flush（连 `--------- beginning of crash` 这行都没写，而 boot 通道同一行写了）。这属于「logcat 对空 buffer 不落盘」的行为，**不是本模块的 bug，但结论上等价于本通道失效**。

**建议修法**（5.5.16 候选 ①）：
- 方案 A（最小）：起动时先向文件写一行哨兵（如 `# crash channel armed at <ts>`），确保文件非空且 mtime 正确 → 至少能区分"没崩溃"与"通道没工作"。
- 方案 B（更彻底）：crash 通道改用 `logcat -b crash -v threadtime` 常驻 + 自读 stdout 落文件，绕开 `-f` 缓冲；或加 `--pid` 为空时定时 `-d` 快照。
- 至少要加**存活断言**：`startRingChannel` 成功后校验 `logFile.length() > 0`（当前只校验 `createNewFile()` 成功，源码 `AutoLogging.java:246`）。

### 4.2 【可观测性缺陷】`maxBootFiles` 排除最旧 boot log 且**清单不留痕**

```
total=5   included=4
```
但清单只列 4 行。被排除的那一个 **`cleaner-boot-1792843391140.log`（6,242,304 B，20:03）在清单里完全不存在**。

源码根因（`DiagnosticFileSection.kt:105-126`）：
```kotlin
val all = dir.listFiles()?.sortedWith(...) ?: emptyList()
val files = all.take(maxFiles)                    // ← 静默截断，all - files 直接丢弃
addText(zip, "$entryPrefix/manifest.txt", buildString {
    appendLine("total=${all.size}")
    appendLine("included=${files.size}")
    for (file in files) { appendLine(...) }       // ← 只遍历 files，从不遍历被排除的
})
```

**为什么这是问题**：第 47 批的核心教训正是「日志里没有 ≠ 没发生」（规则⑨）。这里造成的是**同一个反方向的坑**：清单告诉你「总共 5 个、收了 4 个」，但**不告诉你是哪个被丢了**。而本批被丢的那份恰恰含**重启前现场**（20:01:56~20:03:22），是定位 §1.1 重启原因的唯一现场 —— 我是靠 `auto_logs_tree.txt` 才拿到它的。

**建议修法**（5.5.16 候选 ②）：在 manifest 里追加被排除项，格式建议
```
excluded=1
cleaner-boot-1792843391140.log	size=6242304	modified=1792843391140	reason=maxBootFiles
```

**判读**：pid 10226（= MediaProvider 新进程，uid 10326）在 20:04:23.139 起来、**200 ms 后**（.338）server binder 就注入了，四类快照全部加载成功、`pushed 9 points to native`。**功能无损失**。

**但这暴露了一个真实的设计缺口**：进程启动早期存在一个「无快照」窗口（`HookPolicyCache` 初始化为空 → 任何 FUSE 请求在该窗口内拿到的是**默认策略**）。本次窗口仅 199 ms 且期间无业务请求，所以没出事。若某个应用在这个窗口内发 FUSE 请求，**会按默认策略放行**（= 该拦截的没拦）。

**这不是回归** —— 是第 45 批「桥连上 ≠ 回调注入」同一族的**第三种表现**：这次 binder 注入是及时的，但「注入前」这段现在有 12 行 W 日志（以前是静默的），属于**可观测性变好**。

**建议**（5.5.16 候选 ③，优先级低于 ①②）：
- 把这段降噪为**一行汇总**（`snapshot unavailable during early init: 4 files, resolved in 199ms`），而不是 12 行；
- 若把「策略未就绪」当成安全边界，则应在该窗口内**拒绝**而非放行（需评估对开机体验的影响，不建议贸然改）。
