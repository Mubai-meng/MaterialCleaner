`hookRefresh = 0` ⇒ `MediaProviderHookGateway.registerAndRefreshFromDataBus(server)`
（`LayerOrchestrator.initialize` 第 105 行）**耗时 0 ms** 就返回了。
它走 `whileAlive`，而此时的 `whileAlive`：

```kotlin
if (service == null || !pingBinder()) {        // ← 桥未连上时进入
    if (!tryReconnect(ctx)) return            // ← 被 5s 节流挡住 → 直接 return
```

`initialize` 在 `09:02:43.400` 就跑了，此时桥还没连上；`tryReconnect` 被
`HookBridgeReconnectThrottlePolicy`（5 s）挡住 ⇒ 返回 false ⇒ `whileAlive` 直接 return，
**`c.accept(s)` 一次都没执行** ⇒ `hookRefresh = 0 ms`。

### 3.2 环 2：`establishConnection` 成功后不注入

`CleanerHooksClient.establishConnection`（5.5.11 版本）结尾只有：

```kotlin

service = newService
deathRecipient = newDeathRecipient
MediaProviderHookGateway.onBridgeConnected()
Log.i("MC_REDIRECT", "[CleanerHooksClient] $reason: connected")

```

`onStart` 成功时直接 `cancelStartupRetry(); return`；阶梯成功时 `finishStartupRetry()`
只打一行日志。**两条成功路径都不注入回调。**

而此后再也没有人主动调 `whileAlive`：桥一直活着 ⇒ `service != null && pingBinder()`
⇒ 快路径跳过重连分支 ⇒ 注入语句**永远不执行**。

### 3.3 环 3：MediaProvider 读快照全落文件兜底

`HookDataBusBridge.readSnapshot`（`callback == null` 时的行为）：

```kotlin

if (remote != null) { ... }              // ← callback 为 null，整段跳过
return DataBus.readSnapshot(name)        // ← 只能读文件
```

`DataBus.readSnapshot` → `readRegularText`：

```kotlin
internal fun readRegularText(file: File, label: String): String? {
    if (!isRegularFileNoFollow(file)) {
        if (Files.exists(file.toPath(), LinkOption.NOFOLLOW_LINKS)) {
            Log.w(TAG, "Rejected non-regular DataBus file: $label")
        }

```

**只有「存在但非常规文件」才打 W**。路径不存在或不可达 ⇒ 静默返回 null。

现场表现（9705 从 `09:02:50` 起每 30 s 一轮）：

**两批的差别只有时序**：

| | 第 44 批 | 第 45 批 |
|---|---|---|
| server `onStart` | `21:11:27.237` | `09:02:43.400` |
| MediaProvider `setMediaProviderBinder` | `21:11:29.929` | `09:02:50.381` |
| 桥首次连上 | `21:11:30.997`（attempt 4） | `09:02:51.160`（attempt 6） |
| 之后是否有 `whileAlive` 重连 | **有**（`binderDied` @ 21:12:57.525 → 重连 → 注入） | **没有**（桥一直活着） |

第 44 批是**桥死过一次又重连**，重连走 `whileAlive` 的重连分支，顺带把回调注入了 ——
**故障被偶然绕过**。第 45 批桥一次没死，快路径一直命中，缺陷暴露。

⇒ 这不是「5.5.11 之后的新问题」，而是 **5.5.11 之前就存在、被 5.5.11 的启动阶梯改了时序后才稳定暴露**

5.5.11 补了阶梯，桥在 `onStart` 后 7.76 s 就连上，反而绕过了那条会注入的路径）。

## 5 修法

### 5.1 主修：`establishConnection` 成功后统一注入（`CleanerHooksClient.kt`）

```kotlin
MediaProviderHookGateway.onBridgeConnected()
Log.i("MC_REDIRECT", "[CleanerHooksClient] $reason: connected")

injectServerCallback(ctx.mCleanerServerCallback)
return true
```

新增私有方法：

```kotlin
private fun injectServerCallback(callback: ICleanerServerCallback) {
    val target = service ?: return
    try {
        target.setCleanerServerBinder(callback)
        Log.i("MC_REDIRECT", "[CleanerHooksClient] server callback injected into hooks bridge")
    } catch (e: RemoteException) {
        Log.w("MC_REDIRECT", "[CleanerHooksClient] Failed to inject server callback", e)
        clearDeadConnection()
    } catch (e: RuntimeException) { ... }
}
```

并把 `whileAlive` 重连分支里原来那段 `service?.setCleanerServerBinder(...)` 删掉
（`tryReconnect` 走的正是 `establishConnection`，已注入；重复注入纯属多余 Binder 往返）。

**为什么放在 `establishConnection` 而不是 `onStart`**：`establishConnection` 是
`onStart` / `startupRetry#N` / `tryReconnect` / `whileAlive` **四条路径的唯一汇合点**。
放在这里才能保证「桥一旦可用，回调一定在」。放在 `onStart` 只覆盖开机第一条路径。

### 5.2 副修：把静默降级变成可见（`HookDataBusBridge.kt`）

`readSnapshot` 在 `callback == null` 时补一条按名去重的 W：

```
readSnapshot without server callback (bridge not injected): <name>
  — falling back to direct file read, which this process (uid=10326) normally cannot do
readSnapshot fallback also failed: <name> — snapshot unavailable to this process
```

这直接回答第 45 批的核心困惑：**为什么四类快照全缺却一条 E/W 都没有**。
按名去重 ⇒ 每进程每快照各一条，不刷屏。

### 5.3 守卫（`HooksServerCallbackInjectionContractTest`，3 条）

| 测试 | 断言 |
|---|---|
| `连接建立成功后必须注入 server 回调` | `establishConnection` 函数体内含 `injectServerCallback(`，且位于 `return true` 之前 |
| `全文件注入点唯一` | `setCleanerServerBinder(` 直接调用只 1 处（在 `injectServerCallback` 内，注释不计） |
| `whileAlive 不得自带第二套注入逻辑` | `whileAlive` 函数体内不含 `.setCleanerServerBinder(` |

**反向验证已做**：临时删掉 `injectServerCallback(...)` 那一行后，
第 1、2 条测试立即 `AssertionError`（`HooksServerCallbackInjectionContractTest.kt:70` 与 `:105`）；
恢复后 3 条全绿。

## 8 实机判据（5.5.13，覆盖安装后**必须重启一次**）

> 安装当次跑的是旧字节码（LSPosed 在 zygote 期读成 `InMemoryDexFile`），修复当次必不生效。

| # | 判据 | 期望 |
|---|---|---|
| 1 | `[HooksBridge] setCleanerServerBinder` 出现次数 | **≥ 1**（关键） |
| 2 | `[CleanerHooksClient] server callback injected into hooks bridge` | **≥ 1** |
| 3 | `MediaProviderHooksService.setCleanerServerBinder called, binder=true` | **≥ 1** |
| 4 | `HookPolicyCache ... no snapshot available` | **0 条** |
| 5 | `fuseNativeHook.state` | `HEALTHY`，`nativeSyncVerdict = SYNCED` |
| 6 | `nativeGen` vs `snapshotGen` | 相等（如 `5 / 5`） |
| 7 | `fuseRedirect.redirected` | **> 0**（用夸克网盘等已配置规则的应用验证） |
| 8 | `HookRecoveryCoordinator: nativeGen=0 < snapshotGen=N` | **0 条** |
| 9 | `readSnapshot without server callback` | **0 条** |

判据 1、2 是本次修法的直接指针；3 是它传导到 MediaProvider 侧的证据；
4–8 是最终效果。若 1、2 有而 7 仍为 0，则问题在 `applyConfiguredMountPoints` 之后的 native 侧，
需另开一批。

## 9 一句话总结

**桥在 `09:02:51.160` 就连上了，但 server 从没把回调交给它。**
`CleanerHooksClient.establishConnection` 成功返回时只打日志不注入，
而注入逻辑藏在 `whileAlive` 的「重连」分支里 —— 桥不重连就永不执行。
于是 MediaProvider 只能读文件、读不到四类快照、mount points 永不应用、
`nativeGen` 恒 0，`NativeSyncPolicy` 判 STALE，界面显示「存储重定向降级运行」。
