# 5.5.12 —— 开机握手根因（`directBootAware`）+ 三项诊断自证

> 版本：`562` / `5.5.12`
> 前置：5.5.11（`561`）第 44 批实机验收发现「开机 3.76 s 策略空窗」未达 ≤1 s 目标

---

## 0. 一句话

3.76 s 的真因不是「重试不够快」，而是 `HooksBridgeProvider` 缺
`android:directBootAware` —— **用户解锁前它根本没被 AMS 安装**，server 任何形式的
「拉得更勤」或「反调更快」都无效。修法是 1 行 XML。另附三项诊断自证。

---

## 1. 开机握手空窗（真因与修复）

### 1.1 先纠正我自己在 5.5.11 给的归因

5.5.11 的第 44 批验收报告把 3.76 s 拆成「0.05 s app 未起 + **2.65 s app 主线程忙** +
1.06 s 阶梯粒度」，并建议两条路线：A 压阶梯常量（省 0.9 s）、B app 就绪后反调
（压到 ~0.1 s）。用户追问「B 方案是什么意思」后重查日志，**两条都站不住**：

- app 进程 `21:11:27.290` 就能响应 `BinderProvider.call(sendBinder)`（`onStart` 后 53 ms）
  ⇒ 主线程**不忙**；那段「忙」的观感来自 `Surface` / `DynamicFramerate` 日志恰好与
  解锁时刻重叠，是相关不是因果
- B 方案的前提「app 就绪即反调」不成立：app 早就绪了，缺的是 provider 本身

### 1.2 时间线铁证

```
21:11:27.237  9241  onStart: attempting to get hooks service binder...
21:11:27.238  9241  E HooksBinderRetriever: Failed to get content provider external
21:11:27.290  8960  D MC/Test: BinderProvider.call: method=sendBinder       <- 兄弟 provider 可用
21:11:27.731  4219  W ActivityThread: ... (user not unlocked)               <- 最后一条未解锁告警
21:11:29.031  4219  D UserController: Unlocking user 0 progress 20
21:11:29.077  4219  I UserController.UserState: RUNNING_UNLOCKING -> RUNNING_UNLOCKED
21:11:29.081  4219  V ContentProviderHelper: Installing ContentProviderInfo{name=me.gm.cleaner.hooks_bridge ...}
21:11:29.081  4219  V ContentProviderHelper: Installing ContentProviderInfo{name=me.gm.cleaner.fileprovider ...}
21:11:29.081  4219  V ContentProviderHelper: Installing ContentProviderInfo{name=me.gm.cleaner.androidx-startup ...}
21:11:29.929  8960  W MC_REDIRECT: [HooksBridge] sServerCallback is not yet set (startup)...
21:11:30.997  9241  I startupRetry#4: connected
```

**解锁完成（29.077）到 provider 被安装（29.081）只隔 4 ms。** `me.gm.cleaner.binder`
**不在**这份补装清单里 —— 它在 manifest 里带 `android:directBootAware="true"`，随进程
启动就装好。两个 provider 的差异就在这一个属性上：

| provider | `directBootAware` | 首次可用 |
|---|---|---|
| `me.gm.cleaner.binder` | **有** | 27.290（进程起后 53 ms） |
| `me.gm.cleaner.hooks_bridge` | **无**（5.5.11 及以前） | 29.081（解锁后 4 ms） |

⇒ 正确拆解：**1.844 s 等解锁** + 0.859 s 阶梯粒度 + 1.057 s `establishConnection` 自身。

### 1.3 为什么 A 方案的「改善 63%」不可归因

第 43 批 10,158 ms → 第 44 批 3,760 ms 的差异，主要来自**解锁时刻相对 `onStart` 的偏移**，
不是阶梯起了作用。第 43 批日志未留存 `Unlocking user 0` 行，此结论为推断级，但
第 44 批的因果链本身是实证级：`onStart` 比 provider 存在早 1.84 s，三次重试全部落在
解锁之前，一次都不冤。

阶梯不是白留的：它保证「解锁后尽快再试一次」（#4 在 29.940 发出，解锁后 0.86 s）。
修掉 `directBootAware` 之后，阶梯退化为纯保险（首次即成功，不会启用）。

### 1.4 做法

```xml
<provider
    android:name=".client.HooksBridgeProvider"
    android:authorities="${applicationId}.hooks_bridge"
    android:directBootAware="true"      <!-- 5.5.12 新增 -->
    android:exported="true"
    android:enabled="true" />
```

**为什么不是改握手顺序**：B 方案要新增 AIDL 方法 + 双向依赖，而收益上限已被
「provider 不存在」封死。`directBootAware` 是从根上把 provider 提前到与进程同期，
改动面 1 行、零新协议、零新线程。

**为什么不顺手改 `fileprovider` / `androidx-startup`**：`InitializationProvider`
会拉起 App Startup 的全部 initializer（重活），`FileProvider` 依赖 CE 存储路径配置。
两者都不在启动关键路径上，改了只会增加开机负担。

### 1.5 安全性核查（静态，非推测）

| 检查项 | 结果 |
|---|---|
| 该类 `SharedPreferences\|getFilesDir\|getDataDir\|DataStore\|File*Stream` | **0 命中** |
| `onCreate()` | 只有 `getContext()` + `getApplicationContext()` |
| `sHooksService` | `static final` 匿名 Stub，纯内存 |
| 鉴权路径 | 只走 `PackageManager`（system_server，direct boot 可用） |
| `XposedConnectionState` / `ServerStateMachine` | 均为 `MutableStateFlow`，无持久化 |

`directBootAware` 只改变「何时被安装」，不改变 provider 的上下文绑定方式；
真正需要在 CE 不可用时禁入的逻辑本就不存在。

## 2. `HooksBinderRetriever` 的「取不到 provider」降 W + **配对升级**

### 现象

第 44 批每次开机固定 3 条 E：

```
21:11:27.238  E HooksBinderRetriever: Failed to get content provider external
21:11:27.939  E HooksBinderRetriever: Failed to get content provider external
21:11:28.940  E HooksBinderRetriever: Failed to get content provider external
```

时刻与 `startupRetry#1/#2/#3` 逐一重合，是 5.5.11 同型漏改（那次只降了
`HookBridgeRegistrar` 的 `Unknown authority`）。

### 做法

`CleanerHooksBinderRetriever.java`：`Log.e` → `Log.w`，注释写明两类成因
（app 刚 fork 未 publish / user 未解锁时非 directBootAware 的 provider 在 AMS 里不存在）。

### 为什么同时把「阶梯耗尽」升 E

逐次失败降 W 之后，必须留一个真故障出口，否则「桥永久不存在」（app 被停用 /
崩溃循环 / provider 被裁掉）会全程静音。这与 5.5.11 把
`HOOK.JAVA.REG.EXHAUSTED` 由 W 升 E 是同一条原则。

`CleanerHooksClient` 的 `startup retry exhausted`（11.7 s 窗口跑完）→ `Log.e`。
该日志**有界**（阶梯只跑一轮，不会刷屏），且 5.5.12 起 provider 开机即安装，
此时仍失败只可能是真故障。

### 反向保护

`HooksBridgeSeverityContractTest`（3 条）：

- `if (provider == null)` 分支必须是 `Log.w` 且**不得**出现 `Log.e`（按 `return null;`
  精确切片，避免误读后面的 `catch` 分支）
- `Failed to get hooks service`（拿到了 provider 但 call 抛异常）**保持 E**
- `startup retry exhausted` 必须是 `Log.e`（取离锚点最近的 severity 字面量）

## 3. `preparedPackages` 加时点

### 现象

第 38 / 40 / 44 批**连续三次**出现「`preparedPackages=0` 配 `vfsMountedPids=N`」被读成
「模块自相矛盾」。两者本就不同维度：

- `preparedPackages` = `Mounter.mkdirRecords.keySet().size`（**目标目录已就绪**的包数）
- `vfsMountedPids` = 普查时刻**活着的已挂载 pid** 数（30 秒节流缓存）

目标应用全部退出后 `pruneLocked` → `removeMountDirsLocked` 让前者实时清零，后者仍是缓存。

### 做法

- `VfsReportKeys.PREPARED_PACKAGES_AT = "preparedPackagesAt"`，由 `collectReport` 写入
  （与 `recordedPidsAt` 同一个 `now`、同一次调用）
- 诊断概览在 skew 行**之前**输出：

```
- VFS 就绪：preparedPackages=0 @1759…998（目录就绪数，与已挂载 pid 数不同维度，不是矛盾）
- VFS 采样：实时 recordedPids=0 @1759…998，普查 vfsMountedPids=6 @1759…409，相差=29576ms（…）
```

**缺时点时不打印**（与 `appendVfsSamplingSkew` 既有纪律一致：宁可不打印，也不给可能错的差值）。

单测 `DiagnosticSummaryVfsSamplingTest`（5 条，含反向用例「缺普查值时 prepared 行仍要输出」）。

## 4. `budget=` 文案标明 per-file

### 现象

manifest 里 `budget=bootTiered(1572864B)+ringHeadTail(524288B)` 被读成**整个 auto 目录**
的总预算。实际 `MAX_BOOT_LOG_FILES = 2` 份各自裁剪，实测 `logs/auto/` 3,564,059 B =
声明值的 **1.70 倍**。

### 做法

抽出共用的 `autoLogBudgetSpec()`（`DiagnosticFileSection.kt`），manifest 与诊断概览同源：

```
budget=perFile(bootTiered=1572864B, ringHeadTail=524288B) maxBootFiles=2 bootTotalMax=3145728B
```

分级裁剪文件自己的头部也标作用域：`budget=perFile maxBytes=1572864 …`。
`MAX_BOOT_LOG_FILES` 由 `private` 改 `internal` 以便共用 —— **裁剪行为零改动**，只改自证文案。

单测：`DiagnosticSummaryVfsSamplingTest.budget 文案必须标明 per-file 并算出总数上限`。

## 5. 明确不改（附理由）

| 项 | 理由 |
|---|---|
| 阶梯常量（原 A 方案） | 修掉 `directBootAware` 后阶梯不启用，压常量无收益 |
| app 反调握手（原 B 方案） | 前提被推翻：app 早就绪，缺的是 provider；改协议收益为负 |
| `fileprovider` / `androidx-startup` 加 `directBootAware` | 前者依赖 CE 路径配置，后者拉 App Startup 全部 initializer |
| `DiagnosticSummary` 的 `E Parcel` 归因公式 | 纯文案，需先想清读者视角，不阻塞 |
| `ParceledListSlice` 214 KB reply 瘦身 | 需设计（只传变化项/分页），改错会丢应用列表 |

## 7. 实机判据（覆盖安装后**必须重启**）

1. `onStart` 与首次 `connected` 的时间差 **≤ 100 ms**（不再是 3.76 s）
2. 开机日志里**没有** `startupRetry#` 行（说明首轮即成功，阶梯未启用）
3. `HooksBinderRetriever` 的 `Failed to get content provider external` **0 条**
4. `vfs` 段同时有 `preparedPackages` / `preparedPackagesAt`，概览多一行「VFS 就绪」
5. `auto_logging_manifest.txt` 出现 `budget=perFile(...) maxBootFiles=2 bootTotalMax=3145728B`

> 覆盖安装当次跑的还是旧字节码（LSPosed 在 zygote 期读成 `InMemoryDexFile`），
> 日志会出现 `STALE_SERVER: app=562 server=561 hook=561 installed=562`，**重启自愈**。
