## 2. 5.5.10 验收之一：`StartupTiming` 双写快照 —— 通过，且拿到决定性证据

### 2.1 快照已在

`status/orchestrated_status.json` 出现 `startupTiming` 段：

```json
{
  "attempt": 1,
  "startedAtWallMillis": 1792746215853,
  "completedAtWallMillis": 1792746215915,
  "elapsedMs": 62,
  "segmentsMs": {
    "gateway": 1, "observers": 25, "pkgReceiver": 1, "autoLogging": 7,
    "publishAll": 22, "remount": 0, "hookRefresh": 0, "binder": 4, "scheduler": 2
  }
}
```

**九段之和 = 1+25+1+7+22+0+0+4+2 = 62 = `elapsedMs`**，逐项自洽。
`attempt=1` 说明本 server 进程只跑过一次 initialize（无重建）。

### 2.2 「启动只用了 62 ms」是可信的

`startedAtWallMillis=...853` 对齐 `initialize start` 日志的 `17:03:35.853`；
`completedAtWallMillis=...915` 对齐 `17:03:35.915`。

其中 `observers=25 ms` 是最大项（5 个 observer 启动 + 首次 `RuntimePolicyProjector`
扫描 8 个包），`publishAll=22 ms` 次之（6 份快照落盘），`autoLogging=7 ms`。

### 2.3 日志行仍然丢失 —— 但这次能证明「是被丢弃，不是没执行」

`initialize done in` 在 **三处全部 0 命中**：`cleaner.log`、`.log`、`.log.1`。
`LayerOrchestrator` 在本会话只有 2 条日志（旧会话的 `binderDied` + 本次 `initialize start`）。

**本批拿到了第 42 批没有的闭环证据链**：

1. `StartupTiming.record()` 内部的 `completedAtWallMillis = System.currentTimeMillis()`
   （`StartupTiming.kt:112`）⇒ `...915` 就是 **record 执行的时刻**。
2. `Log.i(TAG, "initialize done in …")` 是 `initialize()` 的**最后一句**，与 `record()`
   **同一线程、顺序相邻**（`LayerOrchestrator.kt:158`）⇒ **`Log.i` 必然紧接着执行了**。
3. 排除「被裁剪丢掉」：boot log 的 `### FOCUSED` 段是**项目 tag 全留**（`step=focused=1`），
   而 `LayerOrchestrator` 是焦点 tag。且该文件从 `35.853` 到 `35.913` **连续记录 pid 9409
   的行**（`initialize start`、`startAllObservers`、`auto logging →` 全在），`35.900` 之后
   该 pid **完全静默**。
4. 排除「白名单没登记」：`LogTagFilter.TAGS` 共 80 项，**含 `LayerOrchestrator`**，
   日志里的 `tags=81` 与之吻合（80 + 通配项）。

⇒ **结论：logd 在 server 启动瞬间按进程配额丢弃了这行。**
`LOG_FLOWCTRL` 的丢弃发生在**日志进入缓冲区之前**，因此任何归档/裁剪策略都救不回来。
这正是 5.5.10 选择「内存事实 + 快照」而非「改日志格式」的原因 —— **该判断被本批证实**。

### 9.2 为什么比上一批长 41 倍

| 批次 | 失败时刻 | 恢复时刻 | 空窗 | 场景 |
|---|---|---|---|---|

（server 17:03:35.679，MediaProvider 17:03:38.312，**仅早 2.6 秒**），
而 Binder 桥要等 app 进程的 `BinderProvider` 可用、桥建好后才能拉快照。

> **本节初版归因有误，已更正。** 初版写「主因是 `HookPolicyRefreshScheduler` 的
> `pollInterval=5000ms`，首次失败后要等最多 5 秒才重试」—— 这个说法不成立。

**真因在 server 侧的桥接重连节奏，不在 hook 侧轮询。**

先说为什么不是 hook 侧：

- 5.5.10 的调度器**首轮立即执行**（`HookPolicyRefreshScheduler.start()` 里的
  `scheduleNext(0L)`），且启动后 60 秒内是 **2 秒**间隔
  （`HookRefreshIntervalPolicy.CONVERGE_INTERVAL_MS`），5 秒只是 60 秒后的稳态值。
  日志里那句 `pollInterval=5000ms` 打印的是稳态常量，不是首轮延迟。
- 更关键的是**这几轮全是空转**：`initFromDataBus` 读不到快照时返回的是
  `SnapshotConsumeOutcome(succeeded = true, changed = false)`，`consumeAfterSignalCapture`
  据此把水位**推进**了（「读不到」被当成「已消费」）；而 `DataBus.getSignalTimestamp`
  在文件不可读时返回 `0L`，于是 `lastXSignalTimestamp = 0`、`isStale()` 恒为
  `0 > 0 = false` ⇒ 调度器既不刷新也不报错。
- 即便 `isStale()` 为真也没用：此刻 `HookDataBusBridge.callback` 仍是 null
  （要 `setCleanerServerBinder` 才赋值），`readSnapshot` 回落到直读
  `/data/local/tmp/cleaner`（uid=10326 无权）依旧返回 null。

真正解开空窗的时间线：

```
17:03:35.853  server 9409  onStart: hooks binder not available yet, will retry
17:03:35.912  app    9031  BinderProvider.call: method=sendBinder      <- 只差 59 ms
      ...... 中间 10.16 秒，没有任何主动重试 ......
17:03:46.016  server 9409  [BinderSender] App process active, triggering server reconnection
17:03:46.018  server 9409  tryReconnect: connected
17:03:46.019  MP     9526  setCleanerServerBinder -> refreshFromDataBus -> gen 3/4 全部加载
```

⇒ `onStart` 取 binder 失败一次后，**10.16 秒内没有任何主动重试**，最终靠
`BinderSender.onActive`（应用回到前台这个事件）把它叫醒。空窗 7.55 s = 这段重连空转，
再减去 MediaProvider 比 server 晚起的 2.6 秒。

### 9.3 影响

开机后 7.55 秒内，MediaProvider 的 **FUSE 重定向与只读规则均不生效**。
期间若应用扫描相册/文件，会看到本应被过滤的内容。

实际影响有限（用户在开机画面/锁屏阶段），但属于**可观测的功能空窗**。

### 9.4 修复（5.5.11）

真正该改的是 `CleanerHooksClient.onStart` 的**启动重连退避**，不是 hook 侧轮询：

| 改动 | 依据 | 预期 |
|---|---|---|
| `onStart` 取 binder 失败后走短退避阶梯 **200ms → 500ms → 1s → 2s**，封顶约 10 s / 8 次 | 本批 17:03:35.912 应用已就绪，`onStart` 只差 **59 ms** | 空窗 **7.55 s → 0.2 s 量级** |
| 稳态路径完全不变 | 阶梯只在 `onStart` 后有限次数内生效 | 长期零额外开销 |

**为什么不去改 `HookPolicyRefreshScheduler`**：那几轮本身就是空转（见 §9.2），
把间隔从 2 s 改成 200 ms 只是往空转循环里多加约 40 次注定无结果的 Binder/文件读，
对空窗零改善，且与「减少系统性能影响」的目标相反。
