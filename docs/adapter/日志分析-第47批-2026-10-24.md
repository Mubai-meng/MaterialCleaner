## 1. 两个隐身开关「看不见」的真因（核心）

### 1.1 事实链

用户上一轮明确反驳：「更多选项最底下**也没有**隐藏桌面图标和隐藏后台相关开关」。
上一轮我给的「滚到底部」解释是错的。本轮重新取证：

1. **确认安装版本**：`manifest.txt` → `versionCode=564`，即 5.5.14。版本判断排除。
2. **确认 XML 存在于 APK**：
   ```
   resource 0x7f150003 xml/service_more_options_preferences
     ()    (file) res/hg.xml   type=XML
     (v30) (file) res/ID.xml   type=XML      ← 关键：有两个变体
   ```
3. **确认 v30 变体内容**：`aapt2 dump xmltree --file res/ID.xml` 的结果中
   `self_hiding|hide_desktop_icon|hide_recents` 命中数为 **0**。
4. **确认默认变体内容**：`res/hg.xml` 里两个节点齐全（line=153/160）。

### 1.2 根因

`app/src/main/res/xml-v30/service_more_options_preferences.xml` 存在（7,904 B，
10-11 建立），它与默认变体**并列**：

- `res/xml/` → API < 30
- `res/xml-v30/` → API ≥ 30

Android 的资源选择规则是**同级目录里配置最匹配的那一份整份胜出**，
**不做节点级合并**。目标设备是 Android 17（API 37）⇒ 只加载 `res/ID.xml`
⇒ 里面没有这两个节点 ⇒ `findPreference` 返回 null ⇒ `?: return` 静默跳过。

5.5.13 增加「本模块」分类时**只改了 `res/xml`**，漏改 `res/xml-v30`。

### 1.3 为什么上一轮会误判（方法论教训）

上一轮的取证是：

```bash
aapt2 dump resources "$APK" | grep service_more_options   # → 只看到 res/hg.xml
aapt2 dump xmltree --file res/hg.xml "$APK"               # → 节点确实存在
```

**这是假阳性**：默认变体里有节点，完全不等于设备会加载它。

**正确姿势**（已写入本报告 §7 检查单）：

```bash
# 1) 先列出**全部**配置变体，不要只用 grep 抓第一个
aapt2 dump resources "$APK" | grep -A4 "xml/service_more_options_preferences"
# 2) 再对**每一个**变体分别 dump
aapt2 dump xmltree --file res/hg.xml "$APK"    # 默认
aapt2 dump xmltree --file res/ID.xml "$APK"    # v30 ← 设备实际加载的是这个
```

同理，`findPreference() ?: return` 的失败**不会**让节点从界面上消失
（XML 里的 `SwitchPreferenceCompat` 照样渲染，只是没有监听器）——
所以「开关完全看不见」这条现象，从代码语义上就已经排除了 `?: return`
是唯一原因，必须往「XML 根本没加载」方向查。这一点当时没做推理闭合。

### 1.4 修复

`res/xml-v30/service_more_options_preferences.xml` 在 `about` 分类之后追加：

```xml
<PreferenceCategory
    android:title="@string/self_hiding_header"
    app:iconSpaceReserved="false">
    <SwitchPreferenceCompat
        android:defaultValue="false"
        android:key="@string/hide_desktop_icon_key"
        android:summary="@string/hide_desktop_icon_summary"
        android:title="@string/hide_desktop_icon_title"
        app:iconSpaceReserved="false" />
    <SwitchPreferenceCompat
        android:defaultValue="false"
        android:key="@string/hide_recents_key"
        android:summary="@string/hide_recents_summary"
        android:title="@string/hide_recents_title"
        app:iconSpaceReserved="false" />
</PreferenceCategory>
```

## 2. `?: return` 静默失败（用户点名要求修）

### 2.1 原实现

```kotlin
private fun bindSelfHidingPreferences() {
    val hideDesktopIcon = findPreference<SwitchPreferenceCompat>(
        getString(R.string.hide_desktop_icon_key)
    ) ?: return                                   // ← 静默
    ...
    val hideRecents = findPreference<SwitchPreferenceCompat>(
        getString(R.string.hide_recents_key)
    ) ?: return                                   // ← 静默
    ...
}
```

一旦第一个取不到，**整段跳过、零日志**。界面上只是"开关不见了"，
日志里一条线索都没有 —— 这次缺陷因此多花了一整轮排查。

### 2.2 新实现

```kotlin
private fun bindSelfHidingPreferences() {
    val hideDesktopIcon = findSelfHidingSwitch(R.string.hide_desktop_icon_key)
    val hideRecents = findSelfHidingSwitch(R.string.hide_recents_key)

    if (hideDesktopIcon == null && hideRecents == null) {
        Log.e(TAG_SELF_HIDING,
            "self-hiding switches absent from the loaded preference XML; ..." +
            "presentKeys=${allPreferenceKeys()}")
        return
    }
    hideDesktopIcon?.apply { /* isChecked + listener */ }
    hideRecents?.apply { /* isChecked + listener */ }
}
```

关键新增：

- `findSelfHidingSwitch(keyRes)`：取不到时打
  `preference not found: key=<解析出的 key> res=0x<资源id>; presentKeys=<全部实际 key>`；
- `allPreferenceKeys()`：递归遍历 `preferenceScreen`，输出**当前加载的那份
  XML 里到底有哪些 key** —— 有了它，"哪份变体被加载"一眼可判；
- 改成 `?.apply {}` 而非整体 early-return：「一个在、一个不在」时仍绑定已有的那个；
- 两个都缺失时额外打一条汇总日志，措辞直接指向「当前变体缺分类」。

## 3. `MC_SelfHide` 未登记 tag 白名单

### 3.1 事实

`SelfHidingPreferences` 的 `TAG = "MC_SelfHide"`（10 处 `Log.x` 调用），
但 `LogTagFilter.TAGS` 里**没有**它。

logcat 的 tag 过滤是**精确字符串比较、无任何通配**，`MC_SelfHide` 不在白名单
⇒ 主环形采集与诊断聚焦日志都**静默丢掉**该 tag。

实测：本批三份 boot log + `cleaner.log` 里 `MC_SelfHide` 命中数 **全为 0**。

后果：5.5.14 新增的 `SelfHidingPreferences.reconcileOnStartup(this)` 是否执行、
是否重新隐藏了图标，**完全无法从日志判断**。

这是第 37 批同一个坑的重犯（那次一次漏了 30 个 tag）。

### 3.2 修复

`LogTagFilter.TAGS` 的「app 侧 UI / 通知」组补上 `"MC_SelfHide"`，
并同步 `LogTagFilterTest` 的 `required` 列表。

## 5. 本批新发现的问题

### 5.1 自动日志目录在归档时只剩 1 个 0 字节文件

**证据**：

```
logs/auto_logging_manifest.txt
  dir=/data/local/tmp/cleaner_logs
  total=1
  included=1
  cleaner-crash.log   size=0   modified=1792822034378   kind=crash

commands/auto_logs_tree.txt
  -rw------- 1 root root 0 2026-10-24 14:07 cleaner-crash.log
  （目录内仅此一个文件）
```

**同一目录在日志里的活动记录**：

```
14:07:14.383  auto logging: ring=8x4096KB crash=2x2048KB boot=60s/2x8192KB tags=81
14:07:14.384  auto logging -> cleaner.log started
14:07:14.385  auto logging crash -> cleaner-crash.log started
14:07:14.386  boot log started: cleaner-boot-1792822034385.log for 60s
14:08:52.029  auto logging stopped: disabled by preference
```

即：三个通道都**正常启动过**，boot 通道还完整跑了 60 秒。用户手上的
`日志.zip` 里也确实有 **8 MB×2 + 122 KB** 的 boot 日志与 **135 KB** 的
`cleaner.log`。

**矛盾**：归档执行 `ls -laR /data/local/tmp/cleaner_logs` 时（14:08，快照时刻）
目录里只剩 1 个 0 字节文件。既没有 `pruned N stale log files`，也没有
`cleanup empty log failed`，目录不是被 `pruneLocked()` 清空的。

**影响**：诊断包丢失了最有价值的两份证据（主环形 + 启动段），
迫使排查只能依赖用户手工导出 `日志.zip`。若用户不知道要单独导出，
诊断包在启动/崩溃类问题上几乎是空的。

**待查方向**（5.5.16）：

1. `AutoLogging.prepareLogsDir()` 会在路径「非符号链接且非目录」时
   `Files.delete(path)`。要确认 14:07:14 启动当刻是否命中该分支；
2. `auto logging stopped: disabled by preference` 发生在归档之前 3 秒
   （14:08:52 vs 14:08:53+）。`shutdownAllLocked` 本身**不删文件**
   （已逐行核对），但它之后到归档之间是否另有清理路径（如 server 重启）；
3. 关键疑点：`Disabled by preference` 说明 `auto_logging` 偏好为 `false`。
   该偏好默认 `true`（`ServicePreferences.autoLogging`），说明用户主动关过。
   **自动日志关闭后，用户手工导出的 `日志.zip` 仍能拿到 25 MB 文件**——
   说明关闭时刻的先后关系需要与用户确认（是不是先关开关、再导出）。

> **判定**：这是**真缺陷**（诊断包丢证据），但根因尚未定位到单一行，
> 需在 5.5.16 用「归档前先把 `AUTO_LOG_DIR` 的 `ls -la` 结果单独落盘 + 记录
> `pruneLocked`/`prepareLogsDir` 的每一次删除」来闭环。**本轮不盲改。**

### 5.2 `SUP.WATCHDOG.RESTART` × 52 —— 疑似第 32 批同类误杀

**证据**：

```
journal.jsonl 60 行 = 52 × SUP.WATCHDOG.RESTART(watchdog-logcat)
                    + 8 × SUP.PROC.DEAD(binder timeout)
按 atElapsed 递减切分 ⇒ 15 个会话
```

`ObserverStallPolicy` 的注释里明确记载了第一次事故：

> 第32批现场：48 条 `SUP.WATCHDOG.RESTART/watchdog-logcat`，全部无 logcat 真死证据。

当时给出的修复是：`CleanerService.getServerException()` 里加了
`probeLogdResponsive()` + `probeFilteredStreamFresh(lastReadAtMs)` 双探针，
**仅对「心跳停滞」分支生效**。

但看代码，`logcat 真死`分支**没有经过这两个探针**：

```java
if (activityManagerObserver.isLogcatShutdown()) {
    return 2;                       // ← 直接返回，无任何旁路确认
}
if (ObserverStallPolicy.isStalled(...)) {   // ← 只有这条走探针
    ...
}
```

而 `isLogcatShutdown()` 的实现是：

```java
public boolean isLogcatShutdown() { return mExecutor.isShutdown(); }
```

`mExecutor.shutdown()` 位于读取循环的 `finally` 块 ⇒ **任何一次循环退出都会让
`isLogcatShutdown()` 永久为 true**，直到 server 进程重建。

因此：只要观察器循环因任何原因退出一次（含可重试的 IOException），
之后每次 `getServerException()` 都返回 2，App 侧 3 次轮询（约 15 s）后
就 `killServerProcess()` —— **这正是「进程活、功能死」被误判成真死的路径**。

**待验证**（5.5.16）：

1. 在 `isLogcatShutdown()` 返回 2 之前加一次 `probeLogdResponsive()`：
   logd 正常响应 ⇒ 说明 logcat 可被重新拉起，不必杀整个 server；
2. 更彻底的做法是给观察器加**重启路径**（当前架构铁律是「不在 server 内重建
   Observer」，需先评审该铁律是否仍适用）；
3. 补一条判据日志：`isLogcatShutdown` 命中时打印
   `mExecutor` 的退出原因（`IOException` 原文 / `InterruptedException` / 正常停止）。

`status/server_exception.txt` 本次归档值为 `0`，说明**采样当时是正常的**——
这与「15 个会话累计 52 次」并不矛盾（每次强杀后重建即恢复正常，直到下次误判）。

> **判定**：高度疑似误杀，但**本轮证据不足以直接改**（缺少
> `ActivityManagerLogsObserver` 循环退出的原始异常——该 tag 未登记白名单，
> 见 §3 同类问题）。5.5.16 先把 `ActivityManagerLogsObserver` 登记进
> `LogTagFilter.TAGS`，下一批才有判据。

### 5.3 `journal.jsonl` 多会话混写、无会话分隔

**证据**：60 行里 `atElapsed` 出现 14 次「递增后突降」（例：
`67596881 → 4966331`、`123508283 → 6385314`），说明 **15 个 app 进程会话
混写在同一个文件里，且没有任何会话边界标记**。

后果：无法判断「这 52 次 watchdog 重启是 15 次开机各 3~4 次，还是某一次开机
连续 52 次」。这直接影响 §5.2 的严重性判断。

另外 `atElapsed` 是 `SystemClock.elapsedRealtime()`（开机后毫秒），
**进程重启后归零**，所以它不是单调量 —— 用它排序本身就是错的。

**建议**（5.5.16）：每条记录加 `atWall`（墙钟）与 `sessionId`（进程启动时刻），
或在文件头写会话分隔行。**注意与既有技术债一致**：`client/errors/journal.jsonl`
无 `atWall` 已在待办里，本轮再次被印证。

## 7. 方法论：资源变体检查单（本次教训的固化）

**任何**「某个 UI 元素在实机上不见、但源码里明明写了」的问题，按此顺序查：

1. **先列全部变体**，不要只 `grep` 抓一个文件名：
   ```bash
   aapt2 dump resources "$APK" | grep -A4 "xml/<your_layout_or_pref>"
   ```
   输出里 `()` 是默认配置，`(v30)` / `(zh-rCN)` / `(night)` 等都是变体。

2. **对每一个变体分别 dump**，逐个确认节点在不在：
   ```bash
   aapt2 dump xmltree --file res/<default>.xml "$APK"
   aapt2 dump xmltree --file res/<v30>.xml     "$APK"   # ← 常被漏掉
   ```

3. **源侧同步核对**：
   ```bash
   ls -d app/src/main/res/xml*
   ```
   只要 `xml-v30` / `xml-land` / `values-zh-rCN` 之类的目录存在，
   **任何**给 `xml/` 加节点的改动都必须同期加进去。

4. **落地守卫**：`PreferenceVariantParityTest` 已把这条规则钉死
   （默认变体有的 key，v30 必须全部有）。以后新增同类变体目录时，
   把新目录加进该测试的变体列表即可。

> **另一条独立的推理纪律**：`findPreference() ?: return` 的失败**不会**
> 让 XML 里的节点从界面消失（节点照常渲染，只是没有监听器）。
> 所以「元素完全看不见」与 `?: return` 在语义上就是矛盾的 ——
> 出现这种矛盾时必须立刻转向「这份 XML 有没有被加载」，而不是继续在
> key 字符串匹配上打转（本轮在此浪费了一轮）。
