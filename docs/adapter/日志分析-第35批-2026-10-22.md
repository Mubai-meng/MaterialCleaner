## 三、但本次跑的仍是**旧字节码**（三条路径修复都尚未生效）

### 3.1 铁证

`E MC_REDIRECT: [XposedInit] Failed to load inline library` 出现 **2 次，每次带 26 行完整堆栈**。

这条文案在 5.5.3 的源码里已经改成**条件打印**（`MediaProviderRuntime.java:122`）：

```java
if (!FuseNativePolicyAdapter.INSTANCE.handleInlineInitFailure(e)) {
    Log.e("MC_REDIRECT", "[XposedInit] Failed to load inline library, ...", e);
}
```

库不可达时 `handleInlineInitFailure` 返回 true ⇒ **不该打印**。日志里打了 ⇒ 跑的不是 5.5.3。

### 3.2 第二条铁证

`applyConfiguredMountPoints` 抛的是 `IllegalStateException: Native hook not ready, state=NOT_LOADED`（28 组 × 11 行 × 2 tag = 616 行）。

而 21:01:23.590 已经 `markUnavailable` 过，`inlineLibrary.reason()` 非空。5.5.3 的代码在这种情况下会抛
`InlineLibraryUnavailableException`（`FuseNativePolicyAdapter.kt:82-86`），走降噪分支。
实际抛的是 `IllegalStateException` ⇒ 缺第34批的 `d6e3352` 修复。

### 3.3 模块路径再次指向另一个旧目录

- 本次安装路径（artd dex2oat 命令行）：`/data/app/~~VUYg-N2eEEiBAQlAEqDuvw==/me.gm.cleaner-mBhmS7tEFlUE26ky6dWHjA==/base.apk`
- 日志里 LSPosed 的 ClassLoader：`/data/app/~~IIy1Fqc.../me.gm.cleaner-.../base.apk`
- 历史路径：5.5.1 = `~~o0Znindb…`、5.5.2 = `~~r5w4mr3…`

**第三次出现「安装路径 ≠ 模块实际加载路径」**，与第34批结论一致：
LSPosed 在 zygote 启动时把模块 APK 读成 `InMemoryDexFile` 并钉死 `nativeLibraryDirectories`，
新 fork 的进程继承旧 dex。**「跑新代码」与「旧库路径消失」互斥。**

### 3.4 状态语义差异（旧代码才会出现）

`state=NOT_LOADED` 而不是 `HOOK_UNAVAILABLE`：旧代码里 `apply` 抛 `IllegalStateException` 后
没有触发 `markInlineRetryExhausted`，状态页因此显示「未加载」而非「不可用」。
5.5.3 起 `apply` 抛专用类型后会落到 `HOOK_UNAVAILABLE`，这个误导会消失——
但同样要「再下一次覆盖安装」才看得到。

## 四、本批新发现的缺陷：启动期两条入口各打一份整栈（已修 `151fa70`）

### 现象

```
21:01:23.594 E MC_REDIRECT: [XposedInit] Failed to load inline library, FUSE native hook disabled
21:01:23.594 E MC_REDIRECT: me.gm.cleaner...InlineLibraryUnavailableException: libinline.so unavailable...
  at ...ensureInlineLibraryLoaded(SourceFile:88)
  at ...initializeInlineHook(SourceFile:0)
  at ...bootstrap.MediaProviderRuntime.initializeInlineHook(SourceFile:26)
  at ...MediaProviderHookModule.onPackageLoaded(SourceFile:79)
  ...（26 行）

21:01:23.606 E MC_REDIRECT: [XposedInit] Failed to load inline library, ...（同一份堆栈）
  at ...MediaProviderRuntime.bootstrap(SourceFile:45)
  at ...MediaProviderHookModule.lambda$hookMediaProviderClass$0(...)
  ...（26 行）
```

### 根因

`MediaProviderRuntime.initializeInlineHook` 的 catch 只做 `markInlineLoadFailed` + `Log.e(整栈)`，
**没有按异常类型分流**。`ensureInlineLibraryLoaded` 抛的 `InlineLibraryUnavailableException`
已经带够信息，这里又完整打了一遍。

且 `sInlineHookInitialized` 在失败时保持 false，所以 **同一个进程里会被两条入口各调一次**
（`onPackageLoaded` 12ms 内第二次来自 `hookMediaProviderClass → bootstrap`）。

### 修复

| 文件 | 改动 |
|---|---|
| `FuseNativePolicyAdapter.kt` | 新增 `handleInlineInitFailure(t): Boolean` —— 命中 `InlineLibraryUnavailableException` 时走一次性闸门并返回 true |
| `MediaProviderRuntime.java` | catch 里改为 `if (!handleInlineInitFailure(e)) { Log.e(整栈) }` |

抽成方法而非让 Java 直接判类型：异常类是 `internal`，且降噪口径必须与 apply / due / cache 共用同一处实现。
净效果：**52 行 → 0 行**（说明由 `ensureInlineLibraryLoaded` 首次标记的那一行承载）。

### 至此四类失败路径全部收敛

| 路径 | 修复批次 |
|---|---|
| `ensureInlineLibraryLoaded` 首轮标记 | 第33批（`35a4332`）：1 行一次性说明 |
| apply / due / `HookPolicyCache` | 第34批（`d6e3352`）：按类型分流，cache 完全静默 |
| 启动期 `MediaProviderRuntime` ×2 | **第35批（`151fa70`）**：按类型分流 |

## 六、UI：副标题断行位置不受控（已修 `2c4cd89`）

### 现象（5.5.3 截图）

```
夸克网盘
已启用 1 条挂载规则、2 条
只读
```

`maxLines=2` 解决了「看不到只读条数」，但断行按字符发生：`2 条` 留在第一行末尾、
顿号也跟着留在行末，第二行只剩 `只读` 两个字。

### 根因

文案是单一文本流 `已启用 %s`，两类规则用 `R.string.delimiter`（`、`）拼接，
TextView 宽度不足时按字符断行，不认语义边界。

### 修复

两类规则并存时用换行符连接：

```
已启用 1 条挂载规则
2 条只读
```

只有一类规则时 `separator` 为空串，仍是单行。
**未改动 `R.string.delimiter`** —— 该字符串另有 15 处引用（Picker / ViewModel 里的 pid 列表等）。
