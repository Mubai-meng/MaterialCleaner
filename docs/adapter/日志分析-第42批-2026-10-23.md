## 1. 会话边界（本轮修正了一处方法论错误）

### 1.1 起机时刻不能用单行反推

此前各批一直用 `boot = audit_ts - uptime` 反推起机 epoch。本轮按此法取 **最后一行**
得 `1792737298.895`（14:34:58.895）；取**第一行**得 `1792737288.696`（14:34:48.696）。
两者相差 **10.199 秒**。

按全量 140 条 audit 行逐条计算 `ts - uptime`，发现它**不是常量**：

| uptime 区间 | 基准跳变 |
|---|---|
| 15.903 → 83.244 | `1792737288.696`（恒定，抖动 ±0.03 s） |
| 83.244 → 84.244 | **+3.233 s** |
| 85.244 → 86.297 | +0.638 s |
| 93.302 → 94.303 | **+3.666 s** |
| 96.303 → 97.304 | +1.320 s |
| 97.304 → 114.317 | `1792737298.895`（恒定） |

即**起机后 uptime 83–97 秒之间，墙钟被 NTP 分四步前移了 10.199 秒**。

**结论**：`audit_ts - uptime` 只能在同一"校时段"内使用。跨段反推起机会差整整一个校时量。
正确做法是**取最早的那批 audit 行**（校时前基准），或显式标注所用基准。

## 6. `recordedPids=0` 与 `vfsMountedPids=4` 并存 —— 不是矛盾，是采样时点差

这是本批最容易误判的一组数据：

```
recordedPids        = 0      ← collectReport 实时读 mounter.pidRecords
vfsManagedPids      = 4      ← census 缓存（sampledAt = 101.8 s）
vfsMountedPids      = 4
srStatus            = com.quark.clouddrive:15750/10479/3; :16096/...; :16357/...; :17360/...
```

`srStatus` 的第三个字段是 `Integer.toHexString(pidFlag)`，`0x3` = `MOUNTED | STARTUP_AWARE`。
`STARTUP_AWARE` 来自 `startUpAwarePids`（= `Mounter.pidRecords`），因此**采样时刻 101.8 s
`pidRecords` 里确实有这 4 个 pid**。

而 `recordedPids` 是在 111.4 s **实时**读的。中间 108.6 s 发生了：

```
14:36:47.532 I ActivityManager: Killing 16357:com.quark.clouddrive:filedownloader (adj 435): stop ... o-stop(40)
14:36:47.536 I ActivityManager: Killing 17360:com.quark.clouddrive:channel (adj 435)
14:36:47.540 I ActivityManager: Killing 16096:com.quark.clouddrive:sandboxed_privilege_process0 (adj 435)
14:36:47.542 I ActivityManager: Killing 15750:com.quark.clouddrive (adj 435)
```

用户从最近任务把夸克划掉 → `ActivityManagerLogsObserver.parseKillingLine` 解析
`Killing <pid>:<pkg>` → `Mounter.notifyProcessKilled(pkg, pid)` → `pidRecords.remove`
→ 4 个 pid 全部移除 → `recordedPids` 归 0，`mkdirRecords` 同步清空（`preparedPackages=0`）。

**结论**：两组数字来自不同时点，**完全自洽**。

### 6.1 但这暴露一个可读性陷阱（建议记录，不必改码）

同一份 `orchestrated_status.json` 里混用了两类指标：

- **实时值**：`recordedPids`、`preparedPackages`、`mountTotalAttempts`（collectReport 当场读 Mounter）
- **30 秒节流缓存值**：`vfsObservedPids`/`vfsManagedPids`/`vfsMountedPids`/`srStatus`
  （`CENSUS_THROTTLE_MS = 30_000`，`collectCensus` 在窗口内直接返缓存）

census 侧有 `vfsCensusAt` 可追溯，实时侧没有。当两批值在 30 秒窗口内因进程启停发生变化时，
报告看起来就像自相矛盾。第 38 批 `mountedPackages=1` 配 `vfsMountedPids=0` 也是同类误读。

**不改代码**（诊断投影不影响行为），但分析纪律上补一条：
**比对外两段指标前，先看 `vfsCensusAt` 与采集时刻的差值。**

## 8. init SIGABRT（pid 8104）—— 与本模块无关，判定依据完整

### 8.1 现象

```
10-23 14:35:04.594  8104  8104 F libc: Fatal signal 6 (SIGABRT), code -1 (SI_QUEUE) in tid 8104 (init), pid 8104 (init)
10-23 14:35:04.609  8104  8104 F libc: Crash due to signal: crash_dump helper failed to exec, or was killed
```

dmesg 对应行（uptime 15.903，与日志时刻**精确吻合**）：

```
avc: denied { ptrace } for comm="crash_dump64"
    scontext=u:r:crash_dump:s0 tcontext=u:r:init:s0 tclass=process permissive=0
```

### 8.2 四条独立证据指向"与本模块无关"

1. **时间上不可能**：崩溃发生在 uptime 15.9 s。本模块最早的进程是 app（9018，uptime 17.1 s），
   server（9362）在 18.6 s。**崩溃时本模块一个进程都还没起来。**
2. **注入面不覆盖 init**：本模块经 LSPosed 注入 `app_process`（app 与 system_server），
   native 侧只 patch MediaProvider 的 `libfuse_jni.so`。init 是 pid 1 的纯 native 进程，
   在 zygote 之前，**不在任何注入路径上**。
3. **形态是 SELinux 拒绝而非崩溃传染**：`crash_dump64` 想 ptrace init 被
   `u:r:crash_dump → u:r:init` 拒绝，所以 tombstone 抓不到（`crash_dump helper failed to exec`）。
   这是 Android 对 init 的保护设计，不是本模块造成的。
4. **同签名一个月前就存在**：crash buffer 里另有
   `11-10 12:57:13.795 pid 1220 (init) Fatal signal 6` —— 同形态、pid 不同。
   按已知规律（logd 会重放 ramoops 旧行），这是**上个月的旧记录**，说明该设备
   的 init SIGABRT 是**长期存在**的现象。

### 8.3 系统未受影响

- dmesg uptime **15.701 → 114.317 单调递增，无回退** ⇒ 未重启、未 framework 崩溃。
- `system_server`(4305) 在 14:35:32 起正常输出，`MediaProvider`(9585) 14:35:09 已 hook 完成。
- 采集时刻五层全 HEALTHY。

**结论**：不计入本模块缺陷。若后续复现频率上升，应作为**设备/ROM 侧**问题单独跟进。

## 11. `client/errors/journal.jsonl` 的 60 条：全部为历史遗留，本次会话零新增

| 检查项 | 结果 |
|---|---|
| 总条数 | 60 |

### 11.1 归属判定（关键）

`ClientErrorJournal` 底层是 `ErrorJournal`，其 `record()` 会**自动补墙钟**：

```kotlin
val stamped = if (event.atWallMillis == 0L) {
    event.copy(atWallMillis = System.currentTimeMillis())
} else { event }
```

而 `ErrorEvent.toJson()` 只在 `atWallMillis > 0` 时写出 `atWall` 字段。

⇒ **60 条全部没有 `atWall`，只可能由引入该字段之前的旧版本写入**（提交 `3848604`，第 32 批）。
本次会话（5.5.9）**零新增**。

### 11.2 旁证

- `atElapsed` 最大 34.31 小时，远超本会话 111 秒 ⇒ 跨多次开机累积。
- `atElapsed` 有 **14 次回退** ⇒ 单调时钟每次开机归零，证明文件确实跨 boot 累积。

## 12. `policyCache.lastGoodGeneration=4` 与 `redirectAppliedGeneration=3` —— 不是矛盾

```kotlin
fun markPolicyCacheHealthy(generation: Long) {
    if (generation > policyCacheLastGoodGeneration) {
        policyCacheLastGoodGeneration = generation
    }
    ...
}
```

`lastGoodGeneration` 是**跨四个域单调推进的最大值**，四个域各有自己的代际：

| 域 | 应用代际 |
|---|---|
| redirect | 3 |
| readOnly | **4** ← 最大值来源 |
| mountPoints | 3 |
| capabilities | — |

所以 `lastGoodGeneration=4`（readOnly 推上去的）与 `redirectAppliedGeneration=3` 并存**完全正常**。
三个 revision 也各自一致：`redirectRevision` 四点相同（`0fe9e62c`），
`readOnlyRevision` 四点相同（`40a37168`），`publisherEpoch` 统一为 `4b10de77-…`。

## 15. boot log 归档只保留前 512 KB —— 60 秒窗口实际只剩约 4 秒

`manifest.txt`：

```
truncation=cleaner-boot-1792737307542.log    keptFirst=524288B dropped=6725632B;
           cleaner-boot-1792737307542.log.1  keptFirst=524288B dropped=7864478B
```

`DiagnosticSummary.kt:96` 对 boot log 用 `keptFirst`（**只保留头部**），其它日志用 `keptHeadTail`。

实测覆盖：

| 文件 | 保留字节 | 行数 | 时间范围 | 覆盖时长 |
|---|---|---|---|---|
| `.log` | 524,288 | 3919 | 14:35:14.233 – 14:35:15.203 | **0.97 s** |
| `.log.1` | 524,288 | 3377 | 14:35:00.539 – 14:35:03.432 | **2.89 s** |

boot log 名义窗口 60 秒、总产 7.2 MB ⇒ 118 KB/s，512 KB 只够 **4.3 秒**。

**后果**：14:35:04（init 崩溃）与 14:35:05–14:35:13 完全不在归档内。
这解释了为什么在 boot log 里 `grep init/crash/tombstone` 返回空 —— **不是没发生，是没被保留**。
本批对 init 崩溃的定性完全依赖 `logcat_threadtime_recent.txt` 的 crash buffer 段（4 行）。

**建议（5.5.10 候选，本轮无改动）**：boot log 的归档策略改为
「头部 + 尾部各 256 KB」，或按 tag 白名单降噪后再存。当前形态在日志洪峰下
实际价值接近于零。
