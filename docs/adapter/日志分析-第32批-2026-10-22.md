## 2 真正的缺陷：48 次无谓的 server 强杀

`client/errors/journal.jsonl` 共 56 条（持久层，跨多次开机累积）：

| code | subject | 条数 |
|---|---|---|
| `SUP.WATCHDOG.RESTART` | `watchdog-logcat` | **48** |
| `SUP.PROC.DEAD` | `RECOVERY binder timeout` | 7 |
| `SUP.PROC.DEAD` | `BOOT binder timeout` | 1 |

同期**没有任何 logcat 真死证据**：

1. `cleaner.log` 里 `ActivityManagerLogsObserver` 的 `Logcat reading loop exited unexpectedly` —— **0 条**；
2. `commands/auto_logs_tree.txt` 显示 `cleaner_logs` 只有一个启动段文件
   （`cleaner-boot-1792651627806.log`），说明**本会话内 server 没有被重启过**；
3. 归档时刻 `serverException=0`。

### 2.1 根因

解码 `ActivityManagerLogsObserver` 里 XOR 混淆的字符串常量（`new char[0x35]` + `^= (i+0x35)%N`）得到真实命令：

```
/system/bin/logcat -s ActivityManager:V -v threadtime
```

`-s ActivityManager:V` 是**只订阅 ActivityManager 一个 tag**。而停滞判定是：

```kotlin
// ObserverStallPolicy
const val STALL_THRESHOLD_MS = 180_000L      // 180 秒没读到行 ⇒ 疑似假活
```

`getServerException()` 命中停滞 → 返回 `2` → App 侧看门狗连续 3 次命中 → `killServerProcess()` + 重启。

**设备空闲时（夜间、无进程启动）ActivityManager tag 本来就没有输出**，logd 完全正常也会读到"停滞"。
这条路径一旦命中，就会在空闲期反复强杀 server —— 48 条记录正是这一类误判。

### 2.2 修复

`CleanerService.getServerException()` 的停滞分支增加**旁路证据**：

```
logcat -d -t 1 -s ActivityManager:V -v epoch
```

取过滤流最新一行的 epoch 秒级时间戳，按「墙钟 − 单调时钟差」换算成 `lastReadAtMs` 对应的墙钟时刻再比较：

| 探针结果 | 判定 | 动作 |
|---|---|---|
| 有行且晚于 `lastRead + 1s` | 我们确实漏读了新行 ⇒ **真停滞** | 返回 2（照旧强杀） |
| 有行但早于 `lastRead` | 那些行已经读过，停滞是假象 | 返回 0 |
| 没有可解析行（`-d` 只打出分隔行） | 过滤流本身就是空的 ⇒ **空闲** | 返回 0 + D 级日志 |
| 探针自身超时 / 异常 | 无证据 | 返回 0（宁可漏杀，不可误杀） |

配套约束：

- **60 秒节流 + 按 `lastReadAt` 缓存**：空闲期每分钟最多 fork 一次，心跳一前进缓存立即失效；
- 判定抽成纯函数 `ObserverStallPolicy.parseEpochMillis` / `isProbeLineFresh`，可单测；
- epoch 取整必须 `round()`：`toLong()` 截断会让 `1792651708.588` 变成 `...587`，在 1s 松弛窗口边界上翻转判定；
- Java 调用 Kotlin 默认参数**不生成重载**，`PROBE_SLACK_MS` 必须显式传（首次构建即踩）。

## 3 另外两处（可观测性）

### 3.1 错误流水跨重启不可归属

`ErrorEvent` 只有 `atElapsed`（单调时钟）。持久层跨多次开机会把 elapsed 重置 ——
本次分析就卡在这里：56 条流水里 `atElapsed` 有 28835 与 67596881 两种量级，
只能靠"数值大小"猜哪条属于哪次 boot，无法排序。

修复：新增 `atWallMillis`，由 `ErrorJournal.record` 统一补齐（调用点显式给出时尊重原值），
JSON Lines 输出 `atWall`。**不参与任何超时判定**，只用于归属与"发生在几点"。

> 注意：`core:common` 的单测没有 org.json 实现（`Method put in JSONObject not mocked`），
> 所以那边只能断言字段，JSON 键靠产物级检查覆盖。

### 3.2 启动期 21 行栈噪声

`IPackageManager.getInstalledPackages(long,int)` 在 API 37 返回 `PackageInfoList`，
直接调用抛 `NoSuchMethodError` —— 这是**预期**的签名变化，反射回退随即生效。
但此前每次都把 throwable 带进日志，每次 server 启动 21 行 W，占该 tag 全部 W 的 95%，
把真正的告警淹没。改为一行 + 异常类名。
