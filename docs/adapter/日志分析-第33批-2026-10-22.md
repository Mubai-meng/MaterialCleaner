## 三、结论二：唯一实缺陷 —— 旧进程 native 库不可达后无限重试刷屏

### 现象

旧 MediaProvider 进程 `32619` 从 `18:33:49.988` 到 `18:34:26.178`，**每 2 秒一次、连续 26 次**：

```
W FuseNativePolicyAdapter: retryInlineHookInitialization failed
W FuseNativePolicyAdapter: java.lang.UnsatisfiedLinkError: LspModuleClassLoader[module=
    /data/app/~~CLq98cFieEB5wU39f2s0Sg==/me.gm.cleaner-Tk6QOVC2DjIUS4f5MJPWKQ==/base.apk, ...
    couldn't find "libinline.so"
    ... (21 行堆栈)
E FuseNativePolicyAdapter: applyConfiguredMountPoints failed: count=8, generation=5
E FuseNativePolicyAdapter: java.lang.IllegalStateException: Native hook not ready, state=FUSE_WAITING
    ... (11 行堆栈)
E HookPolicyCache: loadConfiguredMountPoints: failed
E HookPolicyCache: java.lang.IllegalStateException: ...
    ... (11 行堆栈)
```

调用链（堆栈直读）：

```
HookPolicyRefreshScheduler$scheduleNext$1.run        ← 收敛期 2 秒一轮
 → HookPolicyCache.refreshChangedSnapshotsFromDataBus
   → tryRefreshNativeMountPoints
     → loadAndPushConfiguredMountPoints
       → FuseNativePolicyAdapter.applyConfiguredMountPoints
         → retryInlineHookInitialization
           → initializeInlineHook
             → ensureInlineLibraryLoaded → System.loadLibrary("inline") ← 失败点
```

### 根因

用户覆盖安装 5.5.1 时，APK 的安装目录换成了新的随机路径（日志里出现 `java.nio.file.NoSuchFileException: /data/app/~~CLqNcFieEBNwU...`）。旧进程 `32619` 仍持有**旧的** `base.apk` 路径，`loadLibrary` 必然失败。代码侧有三个问题叠在一起：

1. **`ensureInlineLibraryLoaded` 每次都重新 `loadLibrary`** —— 没有「本进程内已确定不可达」的标记。`System.loadLibrary` 的结果在同一进程内是确定的，重试纯属浪费。
2. **`retryInlineHookInitialization` 在 apply 路径没有任何节流** —— `RETRY_DELAYS_MS`（5s/10s/30s/60s）只在 `retryInlineHookInitializationIfDue` 里生效，而策略刷新是另一条路径，每 2 秒无脑重试一次。实测 26 次全烧在 52 秒内。
3. **失败一律打完整堆栈** —— 21 行 + 11 行 × 2 个 tag，LSPosed 的 `LSPosedFramework` tag 再把同样的栈抄一遍（104 + 78 + 57 行）。

合计单次覆盖安装产生 **500+ 行 W/E 噪声**，把真正的错误埋掉。

### 修复

| 改动 | 位置 | 说明 |
|---|---|---|
| 新增 `InlineLibraryAvailability` | `fuse/InlineLibraryAvailability.kt`（新，99 行） | 纯 Kotlin 状态类：不可达标记（幂等、永久）+ 原因规范化（截 200 字符、空白归一）+ 一次性日志闸门。**可脱离 Android 单测** |
| 捕获 `UnsatisfiedLinkError` 并永久标记 | `ensureInlineLibraryLoaded` | 该错误是 `Error` 不是 `Exception`，必须显式接住；否则上层只能拿到"暂时未就绪"的语义 |
| 抛出类型化异常 | `InlineLibraryUnavailableException`（`IllegalStateException` 子类） | 让上层能区分「不可恢复」与「暂时未就绪」，分别处理 |
| 不可达时短路 | `retryInlineHookInitialization` / `retryInlineHookInitializationIfDue` | 直接返回、不排程、不打堆栈 |
| 状态落到「不可用」 | `retryInlineHookInitialization` catch | 调 `markInlineRetryExhausted`，状态页不再长期停在「等待中」 |
| 失败日志按类型降噪 | `applyConfiguredMountPoints` / `HookPolicyCache.loadAndPushConfiguredMountPoints` | 库不可达只打一行（含原因与"重启进程才可恢复"的结论），其余失败保留完整堆栈 |

**刻意没做的事**：没有给 apply 路径加时间/预算闸门。策略变更原本能立即重试，加了闸门会让挂载点应用最多延迟 60 秒 —— 收益不确定、回归风险实在。本次只消除「不可恢复失败的重试」，不动「暂时未就绪」的收敛行为。

### 预期效果

旧进程场景：`26 次 × 32 行 ≈ 832 行`（含 LSPosed 复抄）→ **1 行**：

```
W FuseNativePolicyAdapter: libinline.so unavailable in this process, native hook disabled
  until process restart (APK replaced? old base.apk path is gone): couldn't find "libinline.so"
```

正常启动场景行为不变（库能加载时标记不生效）。
