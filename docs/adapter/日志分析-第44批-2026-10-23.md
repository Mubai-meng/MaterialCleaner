## 3. 新发现问题

### 3.1 🔴 N1（P2，同型漏改）`HooksBinderRetriever` 仍有 **3 条 E** —— 5.5.12 已修

```
21:11:27.238  9241  9241 E HooksBinderRetriever: Failed to get content provider external
21:11:27.939  9241  9338 E HooksBinderRetriever: Failed to get content provider external
21:11:28.940  9241  9338 E HooksBinderRetriever: Failed to get content provider external
```

时间点与 `startupRetry#1/#2/#3` **逐一重合**（27.238 / 27.939 / 28.940），是同一场景的**伴生 E**：

```java
// runtime/cleaner-server/.../hookbridge/CleanerHooksBinderRetriever.java:36-41
final var provider = SystemService.getContentProviderExternal(AUTHORITY, userId, null, AUTHORITY);
if (provider == null) {
    Log.e(TAG, "Failed to get content provider external");   // <- 启动期 app 未就绪，预期路径
    return null;
}
```

5.5.11 只把 `HookBridgeRegistrar` 的 `Unknown authority` 降成了 W，**漏掉了这一条**。它的语义完全相同（「provider 还不在」），属预期 transient。

**影响**：诊断包 `errors/` 与 `summary` 的 E 计数会把启动期正常握手失败报成故障；同时它计入 ColorOS `LOG_FLOWCTRL` 配额（见 §3.3）。

**修法（5.5.12 已落地）**：`Log.e` → `Log.w`，注释写明两类成因（app 刚 fork 未 publish /
user 未解锁时非 directBootAware 的 provider 在 AMS 里不存在）。

配套**升级**：`CleanerHooksClient` 的 `startup retry exhausted` 由 `Log.w` 改 `Log.e` ——
逐次失败降 W 后，必须留一个真故障出口，否则「桥永久不存在」（app 被停用 / 崩溃循环）
会全程静音。与 5.5.11 `HOOK.JAVA.REG.EXHAUSTED` 由 W 升 E 是同一条原则；该日志有界
（阶梯只跑一轮），不会刷屏。守卫见 `HooksBridgeSeverityContractTest`（3 条，含反向保护）。

### 3.2 🟠 N2（P2）启动窗口 3.76 s 的构成：**1.84 s 等解锁** + 0.86 s 阶梯 + 1.06 s 调用

> **2026-10-23 更正（5.5.12）**：本节初版把不可控段归因为「app 主线程启动繁忙 2.65 s」，
> 并把改进方向指向「改握手顺序（B 方案）」。用户追问「B 方案是什么意思」后重查日志，
> **两点均被推翻**：真因是 `HooksBridgeProvider` 缺 `android:directBootAware`，
> 用户解锁前它在 AMS 里根本不存在，任何「拉得更勤」或「反调更快」的方案都无效。
> 初版的三段拆分与 A/B 方案对比表已删除，作废理由分列在本节末尾。

把「日志时刻 − 阶梯名义值」反解出每次 `establishConnection` 的**自身耗时**：

| 尝试 | 名义 delay | 日志时刻 | 实际间隔 | 反解调用耗时 |
|---|---|---|---|---|
| #2 | 200 ms | 27.939 | 701 ms | **501 ms** |
| #3 | 500 ms | 28.940 | 1,001 ms | **501 ms** |
| #4 | 1,000 ms | 30.997 | 2,057 ms | **1,057 ms** |

⇒ **真实窗口 = Σ阶梯名义值 + Σ调用耗时 = 1,700 ms + 2,059 ms**。设计文档里的
「总窗口 11.7 s / 首次 200 ms」隐含假设「重试间隔 = 阶梯值」，实测不成立。

注意：这 2,059 ms 的调用耗时全部发生在**解锁之后**（#2/#3 的各 501 ms 其实是
「provider 不存在时 `getContentProviderExternal` 的失败往返」，比成功路径更贵；
#4 的 1,057 ms 是真正拿到 binder + `linkToDeath` 的代价）。它解释「解锁后还要
再等 0.86 s」，**不解释**为什么从 `onStart` 起要等 1.84 s。

#### 3.2.1 决定性证据：provider 是被**用户解锁**装进来的

```

21:11:27.238  9241  E HooksBinderRetriever: Failed to get content provider external
21:11:27.290  8960  D MC/Test: BinderProvider.call: method=sendBinder       <- 兄弟 provider 已可用
21:11:27.731  4219  W ActivityThread: ... (user not unlocked)               <- 最后一条未解锁告警
21:11:29.031  4219  D UserController: Unlocking user 0 progress 20
21:11:29.077  4219  I UserController.UserState: RUNNING_UNLOCKING -> RUNNING_UNLOCKED
21:11:29.081  4219  V ContentProviderHelper: Installing ContentProviderInfo{name=me.gm.cleaner.hooks_bridge ...}
```

**解锁完成（29.077）到 provider 被安装（29.081）只隔 4 ms。** 而 `me.gm.cleaner.binder`
**不在**这份「补装清单」里 —— 它在 manifest 里带 `android:directBootAware="true"`，
随进程启动就装好，所以 27.290（`onStart` 后 53 ms）就能响应 `call(sendBinder)`。

对照 manifest 即可确认差异：

| provider | `directBootAware` | 首次可用时刻 |
|---|---|---|
| `me.gm.cleaner.binder` | **有** | 21:11:27.290（进程起后 53 ms） |
| `me.gm.cleaner.hooks_bridge` | **无** | 21:11:29.081（解锁后 4 ms） |
| `me.gm.cleaner.fileprovider` / `androidx-startup` | 无 | 同上（本次未改） |

server 的 `onStart` 落在 27.237，比 provider 存在早了 **1.84 秒**，所以三次失败
（27.238 / 27.939 / 28.940）**一次都不冤**，全在解锁前。

**结论：3.76 s 的正确拆解**

| 段 | 区间 | 时长 | 性质 |
|---|---|---|---|
| 等用户解锁 | 27.237 → 29.081 | **1.844 s** | 被动；改重试节奏压不动 |
| 阶梯粒度 | 29.081 → 29.940 | 0.859 s | 可控 |
| `establishConnection` 自身 | 29.940 → 30.997 | 1.057 s | 可控 |

> 初版的「0.05 s app 未起 + 2.65 s 主线程忙 + 1.06 s 阶梯」三段拆分**作废**：
> app 进程 27.29 已能响应 binder 调用，主线程并不忙；那段「忙」的观感来自
> `Surface` / `DynamicFramerate` 日志恰好与解锁时刻重叠，是**相关不是因果**。

**这同时说明 A 方案的「改善 63%」不可归因**：第 43 批 10,158 ms 与第 44 批
3,760 ms 的差异主要在**解锁时刻相对 `onStart` 的偏移**，不是阶梯起了作用。
（第 43 批日志未留存 `Unlocking user 0` 行，此处只能作推断级结论。）

**修法（5.5.12 已落地，1 行 XML）**：给 `HooksBridgeProvider` 加

### 3.3 🟠 N3（P2）`E Parcel` + `JavaBinder` 占 server 日志 **76.8%**，并触发 3,110 行配额丢弃

**先修正归因**。第 42 批给出的公式 `E Parcel 条数 ÷ inboundHookCallbacks ≈ 18.9` 本批**不成立**（实测 886 ÷ 196 = 4.5）。原因是分子分母方向相反：

- `E Parcel` / `JavaBinder` 是 **server 作为调用方**写 Parcel 时报的（`writeStrongBinder` / `markForBinder`）
- `inboundHookCallbacks` 是 **server 作为被调方**收到的回调数

2. 记录为「已知框架噪声，占 server 日志 3/4，且是启动期丢日志的主因」——避免下次再把「日志缺失」归因成代码路径没走到

`preparedPackages` 的真实语义是 `Mounter.mkdirRecords.keySet().size`（「目标目录已就绪的包数」），**进程全部退出后 `pruneLocked` 会 `removeMountDirsLocked` 把它清零**。本批：

- 21:13:10–21:13:26 挂载了 6 个 pid（`srStatus` 全部 `flags=0x3` = `MOUNTED|STARTUP_AWARE`，**不含 `MKDIR_FAILED(0x10)`** ⇒ 当时目录确实就绪）
- 21:13:59.998 实时读 = 0（夸克 5 个 + DeepSeek 1 个进程已全退，目录已回收）

**两个值都正确，但并列摆放且只有后者带时点**，与 `recordedPids` 是同一类误读陷阱（`recordedPids` 已修，`preparedPackages` 未修）。

**修法（5.5.12 已落地）**：`VfsReportKeys.PREPARED_PACKAGES_AT` 由 `collectReport` 写入
（与 `recordedPidsAt` 同一个 `now`，同一次调用），诊断概览在 skew 行**之前**输出：

```
- VFS 就绪：preparedPackages=0 @1759…998（目录就绪数，与已挂载 pid 数不同维度，不是矛盾）
- VFS 采样：实时 recordedPids=0 @1759…998，普查 vfsMountedPids=6 @1759…409，相差=29576ms（…）
```

缺时点时**不打印**该行（不猜差值），与 `appendVfsSamplingSkew` 既有纪律一致。
单测 `DiagnosticSummaryVfsSamplingTest` 5 条（含「缺普查值仍要输出 prepared 行」的反向用例）。

### 3.5 🟡 N5（P3）manifest 的 `budget=` 会被读成总预算，实际是 per-file

```
manifest.txt:
  truncation=cleaner-boot-1792761087268.log     keptTiered=1572864B overBudget=4931584B;
              cleaner-boot-1792761087268.log.1   keptTiered=1572864B overBudget=6815855B;
              cleaner-crash.log                  keptHeadTail=524288B overBudget=241664B

logs/auto_logging_manifest.txt:
  budget=bootTiered(1572864B)+ringHeadTail(524288B)
```

实际打包：1,573,644 + 1,261,117 + 524,478 + 204,820 = **3,564,059 B**，是声明预算（2,097,152 B）的 **1.70 倍**。

代码事实：`MAX_BOOT_LOG_FILES = 2`，`addAutoLogs` 在 `for (file in files)` 里对**每个** boot 文件都传 `MAX_BOOT_LOG_BYTES = 1536 KiB`（`DiagnosticArchive.kt:396`）⇒ 上限其实是 `2 × 1536 KiB`。

**不是缺陷，是文案误导**。**修法（5.5.12 已落地）**：抽出共用的 `autoLogBudgetSpec()`，
manifest 与诊断概览同源输出，`bootTotalMax` 直接算好，不把乘法留给读日志的人：

```
budget=perFile(bootTiered=1572864B, ringHeadTail=524288B) maxBootFiles=2 bootTotalMax=3145728B
```

分级裁剪文件自己的头部也标了作用域：`budget=perFile maxBytes=1572864 …`。
`MAX_BOOT_LOG_FILES` 由 `private` 改 `internal` 以便共用（裁剪行为零改动）。

### 3.7 🟡 N7（P3）`ParceledListSlice` 每次 reply 200+ KB

`cleaner.log` 中：
```

W ParceledListSlice: Overly large reply size: 214668
```
- `Element #N is N bytes`：**771 条**
- `Overly large reply size`：**58 次**，取值 `98,348 / 107,208 / 214,668 / 215,184 / 222,300`
