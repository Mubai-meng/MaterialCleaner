## 三、根因：进程启动于安装之后，但跑的是旧字节码

这是本次最需要解释的悖论：进程 30347 明明在安装完成 1.2 秒后才启动，为什么不用新代码？

异常消息里的模块路径与本次安装路径**不是同一个目录**：

```
新安装：/data/app/~~r5w4mr3zyvImpdl1tqD-Eg==/me.gm.cleaner-VyYwSfoRjW1RWEmv8EBhEw==/base.apk
异常内：/data/app/~~o0Znindb1Biq7uRFCCKPgA==/me.gm.cleaner-DCQzIVg4R-Sz5YQZzQNNjg==/base.apk
```

完整异常：

```
java.lang.UnsatisfiedLinkError: LspModuleClassLoader[module=/data/app/~~o0Znindb…/base.apk,
  o1[DexPathList[[dex file "InMemoryDexFile[cookie=[0, -5476376669488311712]]"],
  nativeLibraryDirectories=[/data/app/~~o0Znindb…/base.apk!/lib/arm64-v8a,
  /system/lib64, /system_ext/lib64]]]] couldn't find "libinline.so"
```

关键在 `InMemoryDexFile`：LSPosed 在 **zygote 启动时**就把模块 APK 的 dex 读成内存镜像缓存起来了，`nativeLibraryDirectories` 也随之固定为当时的 APK 路径。MediaProvider 进程 fork 自 zygote，继承的就是这份**旧 dex**。

所以顺序是：

1. 20:11:54 覆盖安装 → 新目录 `~~r5w4mr3…` 生效，旧目录 `~~o0Znindb…` 被删；
2. zygote 里仍是 20:07 之前那次开机时加载的**旧 dex**（无第33批修复），且 native 库目录指向已删除的旧路径；
3. 20:11:55 新 fork 的 MediaProvider 继承旧 dex ⇒ `loadLibrary("inline")` 必然失败 ⇒ 收敛期 2 秒一轮、共 59 轮；
4. 20:16:48 重启 ⇒ zygote 重新加载 5.5.2 的 dex ⇒ 新进程路径正确、库加载成功。

**结论：这 59 轮刷屏跑的是旧版字节码。第33批的修复代码一次都没被执行到，因此「新文案 0 次」是必然结果，不能据此判定修复失败。**

## 五、顺着新代码复查：第33批确实留了一个缺口

虽然本次跑的是旧代码，但把日志里的三层调用链拿去对照当前源码，发现**即使跑新代码，每轮仍会打两份完整堆栈**：

```
FuseNativePolicyAdapter.applyConfiguredMountPoints
  → if (!retryInlineHookInitialization())
        throw IllegalStateException("Native hook not ready, state=…")   ← 类型不对
  → catch (t) { if (t is InlineLibraryUnavailableException) 一次行 else Log.e + 整栈 }
HookPolicyCache.loadAndPushConfiguredMountPoints
  → catch (e) { if (e is InlineLibraryUnavailableException) 一行 else Log.e + 整栈 }
```

`retryInlineHookInitialization()` 在库不可达时返回 `false`（第33批加的短路），但 apply 侧对这个 `false` 抛的是 `IllegalStateException`，于是：

- apply 自己的 catch → `else` → `Log.e` + 11 行栈；
- `HookPolicyCache` 的 catch 只认 `InlineLibraryUnavailableException` → 也走 `Log.e` + 11 行栈。

两处都不进降噪分支。本次 689 + 689 条 E 正是这两处打出来的。

### 修复（提交 `d6e3352`）

| 位置 | 改动 |
|---|---|
| `applyConfiguredMountPoints` | retry 失败且 `inlineLibrary.reason()` 非空 ⇒ 抛 `InlineLibraryUnavailableException`；否则维持原 `IllegalStateException`（真的「not ready」仍需整栈） |
| `retryInlineHookInitializationIfDue` 的 catch | 命中 `InlineLibraryUnavailableException` ⇒ `logLibraryUnavailableOnce`，不再重复整栈 |
| `HookPolicyCache.loadAndPushConfiguredMountPoints` 的 catch | 库不可达分支**完全静默**（原先每轮一行 W，59 轮 = 59 行，仍是噪声）；说明由 adapter 首次标记的一次性闸门承载 |

净效果：单次覆盖安装窗口 **1,378 行 → 1 行**，且这一行带原因与「重启进程前不再尝试」结论。状态仍由 `markMountPointsApplyFailed` / `markPolicyCacheFailed` 落到状态页，不丢可观测性。

## 七、结论

1. **本次唯一的错误簇（1,378 行）全部是一个跑旧字节码的进程产生的**，根因是 zygote 缓存了覆盖安装前的 dex 与 native 库目录；重启后归零。
2. **第33批修复未被验证，也没有失败证据** —— 它要等到「5.5.2 → 5.5.3」那次覆盖安装才会真正被执行。`RELEASE-NOTES-v5.5.2.md` 的错误指引已修正。
3. **第33批留了一个缺口**：apply 路径抛的异常类型不对，导致即使跑新代码也会每轮打两份 11 行堆栈 —— 已修（`d6e3352`），单窗口噪声 1,378 行 → 1 行。
4. 第32批看门狗修复继续有效（客户端流水 0 新增）；重启后五层全绿，服务端/模块侧错误流水均为空。
5. `cleaner-crash.log` 里的崩溃是 ColorOS 自身的 `NightModeUtils` 递归，与本模块无关。
6. 主页副标题截断已修（`19fac1c`，`maxLines=2` + 状态列 8dp 间距）。
