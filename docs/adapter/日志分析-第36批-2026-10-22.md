| 22:07:02.892 | `pushed 9 points to native, generation=5`（新快照） |
| 22:07:20 / 22:07:25 / 22:07:49 | `generation=6 / 7 / 8`，逐步收敛 |

### 4.2 链路

```
server initialize() 尚未发布 redirect_policy 快照
  ⇒ HookPolicyCache 拿不到快照（或只有旧 generation）
  ⇒ nativeGen < snapshotGen
  ⇒ NativeSyncPolicy 判 CONVERGING
  ⇒ NativeHookStateMapper 判 RECOVERING
  ⇒ OrchestratedStatus.evaluate() 把它和真故障一起归到 DEGRADED
  ⇒ 状态卡显示「存储重定向降级运行」
```

关键点：**这段时间重定向能力是完整的**——`generation=3` 的 9 个挂载点已经在 native 侧生效，旧策略继续工作。所以用户看到的「降级」与实际能力不符。

### 4.3 修复：区分「启动/收敛中」与「真降级」

原判定把 5 个状态塞进同一个 `setOf`：

```kotlin
// 旧：RECOVERING 与 DEGRADED/UNAVAILABLE/STALE/DISABLED 一视同仁
it.state in setOf(DEGRADED, UNAVAILABLE, RECOVERING, STALE, DISABLED) -> DEGRADED
```

新判定拆成两个集合 + 宽限期：

```kotlin
const val STARTING_GRACE_MS = 30_000L               // 实测窗口 26–33 s
private val COMPAT_FAILURE_STATES = setOf(DEGRADED, UNAVAILABLE, STALE, DISABLED)
private val INITIALIZING_STATES  = setOf(RECOVERING, UNINITIALIZED)

compat.any { it.state in COMPAT_FAILURE_STATES } -> DEGRADED        // 真故障优先
compat.any { it.state in INITIALIZING_STATES } ->
    if (compatInitializingMs in 1..STARTING_GRACE_MS) STARTING else DEGRADED
```

三条设计约束：

1. **真故障优先**：只要有一层 `DEGRADED/UNAVAILABLE/STALE/DISABLED`，哪怕另一层还在初始化，也报 `DEGRADED`。
2. **超时回归降级**：超过 30 s 仍是初始化态 ⇒ 真的卡住了，仍报 `DEGRADED`，不掩盖故障。
3. **默认参数保持历史行为**：`compatInitializingMs: Long = 0L`，`0` 表示不启用宽限。这样 `uninitialized()` 等不感知时间的调用点行为不变——否则它们会静默地从 `DEGRADED` 变成 `STARTING`。

`RuntimeStatusAggregator` 侧用 CAS 固定起点，避免并发采集把「首次进入初始化态」的时刻不断后推、导致宽限期被无限续期：

```kotlin
if (compatInitializingSince.compareAndSet(0L, now)) return 1L
```

因此本批不靠日志猜，而是**把耗时做成结构化输出**：`initialize()` 每一步 `lap()` 计时，末尾单行汇总（稳态只打一行，不刷屏）：

```

  publishAll=.., remount=.., hookRefresh=.., binder=.., scheduler=..)
```

顺带删掉了原来那句恒不打印的 `Log.i(TAG, "initialize done")`（3 份日志里 0 次）。
